# 儀表板下一筆 Miss 與展演重設

## 現場操作

1. 儀表板按「下一筆走 Miss」。這是最長五分鐘的一次性預備，尚未觸發辨識。
2. 手機正常掃描。新版 Fog Node 在讀取快取前，以專用控制金鑰領取指令；儀表板先登記該條碼與既有資料範圍。Node 實際清除該條碼的共享 SQLite 快取，再回報已套用；後續仍經原本的快取查詢與 Miss 事件，不偽造進度。
3. 下一次再掃描可正常 Hit；設定不會持續略過快取。TEST、非 8–14 位數字條碼、明確 bypass 或 local-only 請求不消耗預備。
4. 手機確認收到結果後，查看本輪條碼與新增圖片清單。按「封存本輪新增資料」可批次重設最多二十筆，也可逐筆操作。
5. 重新準備下一筆並再掃描，即可再演示。若只是查看資料，可用逐筆「還原商品與圖片」。

也保留「預先準備指定條碼」入口：直接使用既有 Fog DELETE /cache/:barcode，在掃描前清除指定快取，不需新增的 Node 領取機制。

## 範圍與保護

- 只登記明確準備的條碼。準備前已存在於 Cloud 的商品與圖片不會封存；未登記的歷史資料不自動判定為展演資料。
- 新商品的原條碼會更名為唯一封存碼，保留商品列、ID 與關聯資料；其新增圖片移到忽略版控的 `.artifacts/rehearsal-archives/<task-id>/`。因此原條碼查不到舊展演結果，並可還原，沒有永久刪檔或刪資料表。
- 追蹤資料位於 `.artifacts/rehearsal.sqlite3`，請連同封存資料保留。準備時的圖片清單為基準，僅處理後來新增且符合該條碼命名的圖片。既有商品這輪新增圖片也保留，避免改動原有商品資料。
- Cloud 分析進行中時拒絕重設；Fog 有 pending/processing 佇列時拒絕準備指定條碼／重設，避免稍後補送重建資料。正常佇列及 App 本地歷史均不清除。
- 同一條碼重複準備沿用原登記，不會將本輪新增商品誤標為原有商品。還原前會檢查條碼及圖片衝突，不覆寫下一輪資料。
- 只保證清除 Fog 快取。Cloud 原有商品仍可能直接查表回傳；要展示完整 Vision/Gemini，請使用本輪新商品並提供照片。Miss 是特定快取查詢結果，不等於一定呼叫 AI。
- 僅供比賽專用環境；同條碼同時多用戶掃描不屬於這個展演控制的驗收範圍。重設先等待手機確認，避免剛回傳的 Node 又寫入快取。

## 部署

- 電腦更新 `tools/rehearsal_api.py`、`server/rehearsal_store.py`、`tools/pipeline_dashboard.py`、`server/main.py` 及 `web/pipeline/`；Cloud 與儀表板都必須重啟，且共用此專案 `.artifacts/rehearsal.sqlite3`。
- Pi 更新 `fog/rehearsalControl.ts`、`fog/queryHandler.ts`，執行 `npm run build` 並重啟 Node。**尚未部署的 ded13fa 不支援下一筆自動領取。**
- Node 設定 `FOG_DEMO_CONTROL_ENABLED=1`、`FOG_DEMO_CONTROL_TOKEN=<與儀表板相同專用金鑰>`、`PIPELINE_DASHBOARD_URL=<既有 Tailscale 儀表板位址>`；選用 `FOG_DEMO_NODE_ID` 須與儀表板一致。金鑰不放前端或 Git。
- Node/Python 必須繼續使用相同 `FOG_DB_PATH`，這是現有共享快取設計。Cloud/儀表板也必須連到同一資料庫：沿用一鍵啟動所使用的 `app-sync-server-db-1`。
- 儀表板預設連 Pi `100.86.249.39:3001`／`:3002`；可用 `REHEARSAL_FOG_URL`、`REHEARSAL_FOG_PYTHON_URL` 在後端設定。

## 驗證界線

以隔離 SQLite／圖片目錄測試新增商品封存與還原、既有資料保留、檔案搬移失敗回滾、還原衝突、跨來源拒絕、單次領取及真實清除確認。Node 測試確認同步 SQLite 刪除發生於 ACK 前，觀測器失聯不偽造 Miss。這些不等於 Pi／手機端到端驗收；未以此功能清理既有實際商品。

若程序或電腦恰在檔案搬移／兩個資料庫提交之間中斷，任務可能停留 preparing/resetting/restoring，介面不會宣稱完成。請保留 journal 與封存檔案後檢查，不要手動刪除 `.artifacts`；這是可回復封存，不是跨檔案系統的分散式交易。
