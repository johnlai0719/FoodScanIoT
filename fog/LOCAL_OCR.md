# Fog 快取與離線佇列管理

Fog 已改為中介管理，不再載入本機 OCR。`local_ocr.py` 留作舊版實驗用途，
`LOCAL_OCR_ENGINE` 不會影響目前服務。正常部署只需 `requirements.txt`。

## 查詢流程

- SQLite 有成功快取：立即回傳；舊快取會附帶提示。
- 沒有快取且雲端正常：立即送雲端分析，成功結果存入快取。
- 沒有快取且雲端離線、5xx、408 或 429：先將條碼及照片等分析資料寫入
  SQLite `analysis_queue`，成功寫入後回傳 HTTP 202、`status: queued`、`queue_id`。
- 本地寫入失敗：回報失敗，不宣稱已暫存。Fog 管理服務本身連不上時也不會假稱排隊成功。
- 重複的相同待辦資料共用同一個任務；`TEST` 的不同照片不會互相命中快取。

啟動背景工作依建立順序逐筆補送，連線失敗從 5 秒開始退避，最長 300 秒。
最舊任務重試期間不越過它處理後續任務。400／401 等不可重試的 HTTP 錯誤會標為
`failed`，不阻塞後續任務。服務中斷時的處理中任務在 300 秒租約到期後重新接手。

補送成功後，結果與條碼快取在同一交易提交，並刪除佇列中已完成任務的照片負載。
若雲端已收到請求但回應遺失，補送仍可能再次執行；目前是至少一次傳送，
雲端尚未實作任務冪等去重。

## 狀態與結果

`GET /queue/{queue_id}` 可經 Node（3001）或 Python（3002）查詢，回傳
`pending`／`processing`／`completed`／`failed`，不包含上傳照片。
完成後的 `result` 可供 App 顯示；`TEST` 結果也透過各自的任務編號取得。
202 回覆及狀態查詢均帶原任務的 `request_id`；相同資料重複提交時仍回傳原編號，
讓 App 的結果回報可對上同一次掃描。

App 將任務編號、原 Fog 位址、送出時間等中繼資料保存於 AsyncStorage，
不在此任務紀錄保存照片或健康背景。重啟會恢復第一筆任務，亦可從已保存清單選擇查詢。
每次查詢結束後等待 10 秒再查；網路失敗繼續重試，404 等不可重試錯誤則顯示原因並停止。
離開等待頁保留任務；移除手機紀錄不會取消 Fog 的工作。
結果畫面提交後才移除已完成的手機紀錄，並嘗試回報儀表板 `sync/done`（觀察服務未開啟或離線不阻擋結果）。
排隊耗時使用手機送出至取得結果的時間，含等待；不推算未量到的雲端耗時。
一般條碼亦可於完成後再次查詢快取。

`GET /health` 的 `queue` 顯示各狀態筆數。清除 `/cache` 不會刪除待辦上傳。

Node 與 Python 預設共用 `fog/fog_cache.db`，需要改位置時兩邊設定相同的
`FOG_DB_PATH`（建議絕對路徑）。`CLOUD_API_URL`、`API_SHARED_SECRET` 與原設定相同。

暫存前移除健康背景、裝置 ID 與位置資料。舊版 `X-Local-Only: 1` 請求會被拒絕，
不會自動改成排隊上傳。App 設定已移除本機 OCR 選項。

修改後需重啟 Fog Python 與 Node 服務，App 需載入新版本。

## 可選的儀表板事件

Node 與 Python 均可設定 `PIPELINE_DASHBOARD_URL`。Fog 回報實際快取決策、雲端不可用、已寫入佇列、補送嘗試及結果；不傳照片、健康背景、憑證或原始例外文字。HTTP 分析回應欄位與佇列交易不依賴觀測器成功。演示意圖由允許清單中的 `X-Demo-Scenario`（cloud／miss／cache／queue）傳遞，與真實命中狀態分開。

Node 的 MISS 只代表 Node 未找到快取；後續 Python 可能因併行補送而已經有快取，儀表板會保留兩層實際紀錄。Node 交給 Python 管理層與 Python 真正送雲端是不同事件，避免把內部正規化當成雲端分析。

詳見 [儀表板事件與部署說明](../web/pipeline/README.md)。本輪未更新 Pi。
