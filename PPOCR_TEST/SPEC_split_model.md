# 成分切分模型 — 規格與驗收標準

2026-08-18 訂。實作前先定義目標與驗收，避免「練出來的東西對不上要的」。

> 三個**待決事項**列在最後，需要確認後才動工。

---

## 1. 為什麼是這個任務

添加物層（下游使用者真正看到的那一層）目前漏掉 52 個添加物。
逐一歸因（`miss_additives.py`）：

| 失分原因 | 個數 | 佔比 |
|---|---|---|
| OCR 讀錯字 | 18 | 35% |
| **段內沒切開** | **13** | 25% |
| **切成一大坨、比對不到** | **21** | 40% |

**三分之二的失分在切分，不在讀字。** 而規則已經到頂——`bench_ceiling.py` 量過，
餵**完美文字**（GT 的 `ingredients_raw`）給現有抽取器，清單層也只有 F1 88.9%。

OCR 那一層則已接近飽和：以 Google Vision 當標尺量測（`gap_vs_vision.py`），
PP-OCR 落後的 39 項裡 **det 沒框到是 0 項**（重疊門檻 0.05–0.7 皆同），
全部是 rec 認錯字；而字典約束解碼（`dict_decode.py`）與合成資料 rec fine-tune
兩種介入的添加物層 F1 增益都是 0。

---

## 2. 範圍

### 做什麼

**判斷每個字的位置是不是一個成分項目的開頭。** 逐字二元邊界預測。

### 不做什麼

- 不生成、不改字、不補字、不翻譯
- 不做 OCR 錯字修復（那是另一條線）
- 不做成分段定位（沿用現有規則的 `HEAD` / `TAIL`，見待決事項 A）
- 不判斷是不是添加物（那是下游 `module_a` 的比對規則）

## 4. 驗收標準

### 主要指標 — 添加物層（`sim_match_preset.py`）

下游 `module_a` 會拿清單去比對添加物庫，只有比對出來的才會變成警示。
中間層的指標不能拿來做產品決策——既有結論踩過一次：清單層 F1 打平的兩個
操作點（p_dict 67.6 / p_boxsep 66.8），到添加物層是 70.2 / 72.3，結論相反。

| | 門檻 |
|---|---|
| F1 | **> 70.0%**（現況 PP-OCR + boxsep） |
| 精確度 | **≥ 80%，這是約束不是目標** |

精確度低於 80% 就是在製造假添加物警示。食安 app 的假警示成本與漏讀不對稱，
不可以用精確度換召回換過頭。

### 次要指標 — 清單層（`bench_ceiling.py`）

餵完美文字時要贏過規則的天花板 **F1 88.9%**。贏不過就表示模型沒有學到
規則以外的東西。

### 安全性質 — 機械檢查，不需人工

**正規化後的輸出字元必須是輸入字元的子集**（`score_ocr.normalize` 會去標點，
所以模型補回頓號、統一括號全半形不算違規）。違反的項目直接丟棄。

這保證模型最壞只會**切錯**（碎片配不到添加物，下游無害），
不可能像 VLM 那樣**編造**出看起來像真添加物的名稱——後者實測會直接變成假警示。

## 5. 這個模型修不了什麼

```
52 個漏失
├─ 18 個  OCR 讀錯字      ← 碰不到，屬於 rec 那條線
├─ 13 個  段內沒切開       ← 本模型的目標
└─ 21 個  切成一大坨       ← 取決於待決事項 B
```

**現實目標是那 13 個**，添加物層召回 59.7% → 約 69.8%。
若待決事項 B 決定「展開巢狀」，目標擴大到 34 個。

## 6. 資料

`synth_split.py` 產生的合成資料，已備妥：

- `corpus/split_train.jsonl` 8000 筆
- `corpus/split_val.jsonl` 1000 筆

**為什麼用合成**：GT 的 57 案是汙染紅線，`predictions/` 是同一批案例同樣不能用。
而切分是純文字到純文字，**沒有影像域差距**（rec 合成那條有，上輪淨損 16 項），
且是反向生成——先造清單再序列化，標籤精確而非近似。

**詞彙來源**：`synth_corpus.py` 的 `ADDITIVES` + `FOODS`（法規與添加物表，
與評估集無關）＋ 新增 `FUNCTIONAL` 功能類別詞。後者是因為既有結論診斷出
「劑」是上輪 rec 語料最大的缺口（測試集 99 次、語料 0 次）。

**難度校準**：合成資料最容易犯的錯是太簡單。用現有規則抽取器當標尺調劣化率：

| 丟頓號 / 括號壞 | 召回 | 精確 | F1 |
|---|---|---|---|
| 0.12 / 0.25 | 69.3% | 78.3% | 73.5% |
| **0.17 / 0.33（採用）** | **61.4%** | **74.4%** | **67.3%** |
| 0.20 / 0.40 | 57.0% | 73.5% | 64.2% |
| **真實 PP-OCR 文字（目標）** | **62.5%** | **73.7%** | **67.6%** |

## 7. 模型與實作

**`ckiplab/bert-base-chinese-ws`**（中研院 CKIP 的中文斷詞 checkpoint）。

選它而不是 base 的理由：斷詞與本任務**結構完全相同**——都是逐字二元邊界預測、
都是繁體中文。從已經學會找中文邊界的 checkpoint 起步，收斂較快，8000 筆也更夠用。

備選：`ckiplab/albert-base-chinese-ws`（更小更快）。

**已知實作坑**：BERT 上限 512 token，而成分段可能超過 600 字
（c58 的 GT 是 596 字，OCR 文字更長）。必須用**滑動視窗加重疊**，
合併時取視窗中央的預測（邊緣上下文不完整）。不處理的話最難的
c57/c58/c59 會壞掉。

**環境成本**：torch + transformers + accelerate 約 2.5GB（目前未安裝），
CKIP 模型約 400MB。訓練本身在 RTX 4060 上約數分鐘。

## 8. 待決事項

### A. 範圍：要不要也讓模型找成分段？

| | 範圍 | 誰找成分段 |
|---|---|---|
| **A1（建議）** | 只做切分 | 現有規則的 `HEAD` / `TAIL` |
| A2 | 找段落 ＋ 切分 | 模型 |

**建議 A1。** 量測支持：那 13 個「段內沒切開」的案例，段落**都有找到**
（c38 的 `多磷酸鈉`、`關華豆膠` 都在抽取器產出的範圍內，只是沒被切成獨立項目）。
段落定位不是失分點。

選 A2 的話合成資料要重生（加入營養表、地址、行銷文案的干擾），
驗收要多一個「段落命中率」指標。

### B. 巢狀慣例 — **已查明，不需要決定**

2026-08-18 用 `audit_nesting.py` 完整盤點 107 個含括號的複合項（26 案）：

| 慣例 | 個數 |
|---|---|
| 整團保留 | 51 |
| **全部展開** | **0** |
| 部分（內部成分也單列） | 56 |

**「全部展開」是 0 個——GT 的慣例是一致的。**

那 56 個「部分」全是巧合：逐一檢視比例最高的（c57 4/6、c59 3/5、c58 2/3），
重疊的都是 `食鹽`／`味精`／`醬油`／`蔗糖`／`水`／`麥芽糊精` 這類極常見的原料——
它們在實體標示上本來就出現多次（不同料包各有一份），所以既單列又出現在複合項內。
**不是刻意展開，是同一種成分真的出現在兩個地方。**

> 早先報告的「52 個展開 vs 39 個不展開」是錯的，來自一個把巧合算進去的粗糙
> regex。**沒有慣例衝突，也不需要重整 GT 或升版本號。**

連帶更正：那 21 個「切成一大坨」的漏失**不是慣例差異造成的**。
c44 的情況是抽取器把 GT 分開列的多個**頂層**項目併成一個 316 字的項目，
屬於真正的頂層邊界失敗——正是本模型的目標，不受任何慣例決定影響。
