# PPOCR 基準線與 fine-tune 評估

目的：決定「自己標註並訓練 PaddleOCR」值不值得做、該訓練哪一段。
2026-08-14 建立。

## 為什麼要重做基準線

舊結論「PPOCR 效果很差」來自 `APP-sync-server/測試/圖片掃描處理/萃取結果報告_PaddleOCR.md`。
那份報告的量測條件有三個問題，疊起來使它量到的不是 PPOCR 的能力：

1. **輸入不具代表性**——用的是 254×400、290×400 這批早期網路圖，不是 App 實際
   送出的手機照（測試集 c24 之後是 3024×4032）。
2. **`local_ocr_api.py:239` 做 `cv2.resize(w*3, h*3, INTER_CUBIC)`**——在已經很小的
   圖上放大馬賽克，不會生出資訊。
3. **PaddleOCR 的 `text_det_limit_side_len` 預設 960 且 `limit_type='max'`**——
   3024×4032 的照片進偵測前會被縮到 720×960。

另外那份報告標題寫「繁體中文優化版」是誤解：`paddleocr/_pipelines/ocr.py` 的語言
對應邏輯裡，PP-OCRv5 把 `ch` / `chinese_cht` / `japan` 全部指到同一個
`PP-OCRv5_server_rec`，**`lang="chinese_cht"` 在 v5 是空操作**，只有降到 PP-OCRv3
才有真正的 `chinese_cht` 模型。所以輸出夾雜簡體，才需要 OpenCC 轉回來。

## 怎麼跑

```bash
python run_baseline.py --preset=v5_hires      # 推論，存 out/<preset>/<case>.json
python score_ocr.py    --preset=v5_hires      # 評分報告
python score_ocr.py    --compare v5_default v5_hires
python score_ocr.py    --preset=v5_hires --detail c38_科學麵   # 單案逐字對照
```

`v5_default` 復刻舊設定（偵測端降採樣到 960），`v5_hires` 解除降採樣到 2048。
兩者用的模型相同，差異可直接歸因於解析度。

> `v5_server_hires` 這組其實與 `v5_hires` 等價——`lang="chinese_cht"` 本來就會
> 選到 server 模型。留著只是為了讓「明確指定模型」這件事在設定裡看得見。

## 指標設計

**主要指標是「成分逐項命中」，順序無關。** 對 `ground_truth/` 每個 case 的
`ingredients_list` 逐項檢查有沒有出現在 OCR 全文裡。

**不用整段字串的 CER 當主指標**，因為它對行序敏感而 OCR 的行序本來就跟人閱讀
的順序不同（營養表多欄、成分分成麵包/油包/粉包、旁邊夾行銷文案）。實測
c38_科學麵 被 CER 記成「錯 104 字 / GT 154 字」，但逐行看幾乎全對——那 104 是
排序造成的假象。CER 仍保留為輔助欄位，但**不可單獨引用**。

不列百分比，只列筆數與清單（沿用量化測試集的既有原則）：
「漏了哪 92 個成分」是工作單，「命中率 88%」不是。

繁簡差異另外一欄計算：模型輸出簡體是字集問題（換模型或後處理即可），
與「認錯字」的修法完全不同，混在同一個數字裡會誤導該做什麼。

## 2026-08-14 基準線結果（58 案 ＝ v2.2 的 48 案 ＋ v3.0 的 10 案）

> （同一批案例、正解有修訂）。OCR 輸出未重跑，只是重新評分。

**注意這 58 案跨兩個主版本**，依測試集規則不同主版本的數字不可相比；
此處的合計只是為了看 OCR 的整體行為，不是可跨期引用的分數。

下列數字是**正解修正後**重算的（同一批 OCR 輸出，只是尺變準了）。
修正前為：GT 767 項、完全命中 563、近似 112、沒讀到 92。

| 項目 | 數字 |
|---|---|
| 成分逐項 | GT 752 項：完全命中 571、近似命中 108、**沒讀到 73** |
| 營養數值 | 檢查 878 個：**漏 66** |
| 繁簡差異 | 227 字（非辨識錯誤） |
| CER（輔助） | v5_default 2370 → v5_hires 2190 字 |

### 結論：偵測不是瓶頸，不要先去框圖

- **det 沒有明顯在漏。** 逐行檢視最差的案例，成分文字都被框到了且信心 0.83–0.94。
  c58_拉麵道「海藻酸钠）、水、食鹽、乳化油（甘油、精製大豆油…」對照 GT 幾乎逐字吻合。
- **rec 在乾淨區域接近可用。** c38_科學麵「通粉、精製油（棕欄油、抗氧化劑混合濃縮
  生育醇）、食鹽、水、味精、」只錯 `麵→通`、`磷→碳`。
- **最大的失分是行序／版面重建**，那是 fine-tune det 或 rec 都碰不到的一段。
- 那 92 個「沒讀到」的成分裡，大宗是 GT 把整塊巢狀配方當成一項
  （如 c37 的「漢堡{麵粉, 水, 糖, 人造奶油, …}」），不是真的沒讀到。
  **這是 GT 格式與比對方式的落差，不是 OCR 失敗**，解讀時要扣掉。
- **c24_優質蛋白奶原本漏 17/21，查出來是正解錯了不是 OCR 讀不到**：那份 ground_truth
  整包是 c23_in果凍的資料（name 寫「in果凍(綜合礦物質)」）。照片本身清晰，
  OCR 幾乎逐字讀對真實標示。2026-08-14 已由 `edit_gt.py` 修正，現在 11/11 完全命中。
  這也是「用 OCR 輸出反查正解」值得做的證據——一個未微調的模型抓出了正解檔的錯誤。

### rec fine-tune 仍然有兩個明確目標（且都不需要人工框圖）

1. **繁體原生輸出。** 現在靠 OpenCC 簡轉繁，而簡→繁是一對多：
   `面→面/麵`（instant_noodle 類別直接受影響）、`干→干/乾`、`松→松/鬆`。
   OCR 輸出常是破碎片段，OpenCC 的詞庫在片段上幫不上忙。
2. **添加物化學名詞彙。** 誤判集中在這一組，且全是添加物用字：
   `鈉→納` 6、`鳥→烏` 5、`呤→冷` 3、`櫚→欄` 3、`磷→碳` 3、`嘌→螺` 2、`苷→甘` 2。
   對應 嘌呤／核苷／棕櫚／磷酸鈉——正是 module_a 要比對的詞彙。

訓練資料以**合成**為主（官方建議 ≥5000 行，真實:合成:通用 ≈ 1:1:1，用 config 的
`ratio_list` 控制）。語料現成：添加物資料庫、58 案的 `ingredients_raw`、
營養標示的固定詞彙。

### 紅線

**不可拿 `測試/量化測試/` 的 v2.1 影像當訓練資料。** 那是評估集，訓練過就失去
跨版本比較的意義。訓練圖要另外收。

## 合成訓練資料（2026-08-15）

rec fine-tune 的第一塊。**零人工標註**，所以能在投入 200–300 張 det 框選「之前」
就回答「fine-tune 到底有沒有用」。

```bash
python synth_corpus.py build --n=6000        # 產語料 → corpus/synth_lines.txt
python synth_corpus.py check corpus/synth_lines.txt   # 污染檢查（必跑）
python synth_render.py                       # 渲染 → FoodScanData/train_rec/synth/
python synth_validate.py --n=300             # 難度校準
```

### 污染防線

**不只是「不能拿測試集的圖去訓練」——測試集的正解文字也不能當語料。**
拿 `c58` 的 `ingredients_raw` 去渲染，rec 模型會學到那串字的序列先驗，
之後在 c58 上的分數就被灌水。這與 `score_eval.py` 廢止 `ingredient_types`
的理由相同：受測對象與正解同源就不叫評估。

語料只來自公開法規詞彙與 `additives` 表（`--from-db`，需 PostgreSQL）。
而「乾淨」不靠宣稱，靠 `check` 驗證，兩道互補的檢查：

1. **連續 3 個成分的順序重疊**——單一成分名重疊無所謂（產業共用字彙），
   順序才是洩漏
2. **連續 25 字以上的字元重疊**——門檻 25 是因為單一長成分名本身就有近 20 字

檢查器本身也驗證過：植入三種污染（整段照抄／連續 3 成分／部分抄襲）全數抓到，
離開碼 1 可當閘門。目前 6000 行語料：**0 行污染**。

### 難度校準——這一步不能跳

合成資料最常見的失敗不是做不出來，是**做得太乾淨**。

| 版本 | CER（未微調 PP-OCRv5_server_rec） | 判讀 |
|---|---|---|
| 第一版 | **0.23%**（5576 字錯 13 字） | 太簡單，訓練學不到東西 |
| 加 `lowres` 後（下限 11px） | 10.24% | 難度夠，但崩壞樣本過多 |
| **下限調到 15px（現行）** | **5.42%**，崩壞樣本 1.7% | 可以訓練 |

第一版太簡單的原因：直接用 48px 渲染，正好等於 rec 模型的輸入高度，**全程沒有
任何資訊損失**。而真實照片裡讀錯的字，行高只有 15–25px（從 3024×4032 裁出小字行
再放大到 48px），糊掉的是那一段路。所以 `deg_lowres`（縮小再放大）是所有退化裡
最關鍵的一項，權重也給最高。

其餘四項退化刻意對齊 `cases.json` 的 `difficulty` 標籤（`curved`／`crease`／
`glare`／`blurry`），這樣「合成資料補強了哪一類」與「哪一類的實測分數上升」
才能互相印證。

> `deg_curved` 第一版把映射寫反了（用 `sin` 而非 `arcsin`），導致邊緣被拉伸而非
> 壓縮，「脫」被撕成「月兌」——圖上顯示的字與 label 不符，比不加退化更糟。已修正。

### 有效代理的證據

合成資料上的形近字誤判，與真實照片上的**是同一組**：

| 誤判 | 合成資料 | 真實照片 |
|---|---|---|
| `櫚→欄` | 3 | 3 |
| `鈉→納` | 2 | 6 |
| `蘿→罐` | 2 | 2 |
| `蔔→葡/萄` | 1 | 4 |

難度對、而且錯在同一個地方，這批資料才算是有效的訓練代理。

## rec fine-tune（2026-08-15 首次執行）

### 環境

`tools/train.py` 與 `configs/` 不在 pip 套件裡，要 clone repo：

```bash

pip install scikit-image lmdb rapidfuzz albumentations albucore   # requirements.txt 缺的
```

訓練權重（**不是** `~/.paddlex` 裡的推論模型，那個不能當 `pretrained_model`）：

```
https://paddle-model-ecology.bj.bcebos.com/paddlex/official_pretrained_model/PP-OCRv5_server_rec_pretrained.pdparams
→ PPOCR_TEST/pretrain/   （205 MB）
```

### 執行

```bash
cd D:/FoodScanIot/PaddleOCR
python tools/train.py -c ../PPOCR_TEST/configs/rec_foodlabel_ft.yml
```

設定與 stock config 的差異都寫在 yml 的註解裡。要點：

| 項目 | stock | 這裡 | 理由 |
|---|---|---|---|
| `epoch_num` | 75 | 20 | 75 是從頭訓練的規模；fine-tune 跑太久會災難性遺忘 |
| `learning_rate` | 5e-4 | 5e-5 | 從頭訓練的 LR 會把預訓練沖掉 |
| `first_bs` | 128 | 32 | 8GB 顯存。實測 bs=16 只吃 2.5GB 太浪費，32 吃 4.1GB |
| `num_workers` | 16 | 2 | Windows 的 dataloader 走 spawn，開太多會卡住 |
| `distributed` | true | false | 單卡 |

**字典不要換。** 實測 8000 行語料的 487 種字元被 `ppocrv5_dict.txt`（18383 字）
100% 涵蓋；換字典會讓分類頭整層失效，205MB 的預訓練權重就白費了。

### 驗收方式——不要看 val acc

合成資料上的 acc 再高也不代表真實表現，分布本來就不同。真正的驗收是在
**58 案真實照片**上比較：

```bash
cd D:/FoodScanIot/PaddleOCR
python tools/export_model.py -c ../PPOCR_TEST/configs/rec_foodlabel_ft.yml \
  -o Global.pretrained_model=../PPOCR_TEST/output/rec_foodlabel_ft/best_accuracy \
     Global.save_inference_dir=../PPOCR_TEST/output/rec_foodlabel_ft/inference

cd ../PPOCR_TEST
python run_baseline.py --preset=v5_ft
python score_ocr.py --compare v5_hires v5_ft
```

`v5_ft` 這組**只換 rec、det 與 v5_hires 完全相同**，所以量到的差異可以歸因於
rec 訓練，不會混進偵測端的變化。

要看的兩個數字（fine-tune 的兩個目標）：

1. **繁簡差異 227 字** → 應該趨近 0
2. **`鈉→納`×6、`鳥→烏`×5、`呤→冷`×3、`櫚→欄`×3、`磷→碳`×3** → 應該減少

若這兩項沒動，代表合成資料這條路不足以達成目標，**此時該停下來重新想，
而不是去標 200-300 張 det**——那是更貴的投資，值不值得取決於這一輪的結果。

## 第一輪 fine-tune 結果（2026-08-15）

在 58 案真實照片上比較（`score_ocr.py`）。**det 完全相同，只換 rec**，
所以差異可歸因於 rec 訓練。

| preset | 完全命中 | 近似 | 沒讀到 | 繁簡 | 營養漏 | 目標形近字 |
|---|---|---|---|---|---|---|
| `v5_hires`（未微調） | 583 | 113 | 93 | **234** | 66 | **21** |
| `v5_ft_ep2` | 582 | 98 | 109 | **1** | 75 | **3** |
| `v5_ft_ep6` | 567 | 107 | 115 | 2 | 63 | 4 |
| `v5_ft`（ep19 best） | 535 | 135 | 119 | 2 | 81 | 2 |

### 兩個目標達成，但整體是淨損

- **繁簡 234 → 1**、**目標形近字 21 → 3**（`鈉→納` 6→0、`櫚→欄` 3→0、`磷→碳` 3→0）。
  合成資料**確實遷移到了真實照片**——這是這輪要驗證的核心假設，答案是肯定的。
- 但 `沒讀到 93 → 109`、`營養漏 66 → 75`。**完全命中幾乎沒動（583→582）**，
  代價卻是多漏 16 個成分。以主要指標看，這一輪是淨損。

### 訓練愈久愈糟，而合成 val 看不出來

`完全命中` 隨 epoch 單調下降：582（ep2）→ 567（ep6）→ 535（ep19）。
而合成資料上的 val acc 在 epoch 10 就飽和到 ~1.0，**`best_accuracy` 這個
checkpoint 選擇機制在這裡完全失效**——它挑到 ep19，是最差的一個。

**教訓：checkpoint 要用真實評估集選，不能用合成 val。**
`run_baseline.py --rec-dir/--out-name` 就是為了讓這種掃描能一行跑完而加的。

### 退步的原因：語料覆蓋缺口

實測：訓練語料涵蓋測試集 91.4% 的字次，但缺 140 種字，其中
**`劑` 在測試集出現 99 次、語料 0 次**——手寫詞彙表只收了物質名
（混合濃縮生育醇），漏了功能類別詞（抗氧化劑、乳化劑、粘稠劑、品質改良用劑）。

診斷證據：

```
剂 → 卜   0 → 7      卜 在語料裡很常見（胡蘿蔔），劑 完全沒有
甘 → 苷   0 → 4      苷 語料 136 次，被過度預測
抽 → 酸   0 → 3      酸 語料裡極常見
```

模型把語料裡常見的字**過度預測**、把語料裡沒有的字**吐不出來**。
再看新增漏掉的 28 項成分，**36% 含「劑」**，而 GT 全體只有 11%——
超額代表 3.3 倍。

### 結論與下一步

方法本身有效（合成→真實的遷移成立），問題出在**語料是手寫的、必然有缺口**。
修法依序：

1. **用 LLM 生成語料**取代手寫詞表——手寫不可能窮舉功能類別詞、
   包裝慣用句式。生成後仍走 `synth_corpus.py check` 過濾污染。
2. **補 1:1:1 的通用中文資料**（這輪跳過了）——防止輸出分布向食品詞彙collapse。
3. **訓練 2–4 epoch 就停**，並用真實 58 案選 checkpoint。

在 1 與 2 做完之前，**不要去標 200–300 張 det**：那是更貴的投資，
而目前的證據顯示 rec 這條路的瓶頸在資料組成，不在標註量。

## det fine-tune 可行性測試（2026-08-15）

**結論先講：「刪碎框」學得到，「營養表整列一框」連過擬合都做不到。**

### 資料

自行拍攝 11 張便利商店貨架照（`FoodScanData/Upload_New`，HEIC 轉 JPG 時用
`ImageOps.exif_transpose` 把方向烙進像素），人工標註 9 張、279 框。
標註策略是「刪掉 det 產生的碎框、改用完整的直排框，營養表則整列一框」。

自動補了 34 個 `###` 忽略框：使用者未框、但落在商品標示範圍內的文字。
不補的話那些區域會被當背景，等於教模型「這裡沒有字」。範圍外的（背景貨架
商品）維持不框——那是刻意要抑制的。

### 訓練圖必須先縮到推論的尺度

第一次訓練用原始 4284×5712，**這是錯的**：推論時
`text_det_limit_side_len=2048` 會把整張縮到 0.36 倍，而訓練若從原解析度
`RandomCrop` 640×640，模型看到的字比推論時大 2.8 倍。就算 loss 降下來，
套回實際推論也對不上。

改成先產生 `FoodScanData/train_det_2048/`（長邊 2048、座標同步縮放）。
順帶讓每張從 24MP 變 3MP，`avg_reader_cost` 從 4.16s 降下來，
整輪從 90 分鐘變 8 分鐘。**對齊是為了正確性，變快只是附帶。**

### 三組量測，方向一致

| | 微調前 | 微調後 |
|---|---|---|
| 訓練集 hmean（7 張） | 0.607 | **0.637** ↑ |
| 驗證集 hmean（2 張） | 0.580 | 0.563 ↓ |
| 58 案 沒讀到 | 65 | 73 ↓ |
| 58 案 營養漏 | 60 | 68 ↓ |
| 58 案 完全命中 | 630 | 629（雜訊內） |
| 58 案 總框數 | 4038 | 3774（−7%） |

loss 5.73 → 4.96。**模型確實在學，學到的是「少框一點」**——precision 上升、
recall 下降、總框數減少，三組量測方向一致，不是雜訊。但那是表面規律，
不是「哪些該框」的判斷；7 張圖、120 個梯度步不足以泛化。

### 「營養表整列一框」失敗——而且不是資料量的問題

在**模型背過的訓練圖**上量營養表區域的框寬（IMG_3977）：

| | 框數 | 寬度中位數 | 寬扁框（寬>2.5×高） |
|---|---|---|---|
| 人工標註 | 11 | **495 px** | 11 / 11 |
| 微調前 | 20 | 127 px | 5 |
| 微調後 | 17 | **122 px** | 6 |

**連過擬合都做不到。** 框數略降（20→17）但寬度幾乎沒動。

原因是幾何上的矛盾。實測營養表的間隙：

```
c57  欄間水平間隙 122px  vs  列距 80px   → 比值 1.52
c28  欄間水平間隙 152px  vs  列距 74px   → 比值 2.04
```

**要模型跨越的空白，比不能跨越的空白還大。** DB 是分割式的，靠局部像素判斷
「這裡是不是文字」；要它在較寬的欄間空白上預測「有文字」、同時在較窄的列距上
預測「沒文字」，這個判斷在局部是矛盾的，必須理解整張表格結構才做得到。

「泛化不了」可以靠加資料，「連背都背不起來」不行——這是表示法與模型歸納偏好
的衝突。

### 給後續的建議

| 標註策略 | 學得到嗎 | 建議 |
|---|---|---|
| 刪掉碎框、直排整條 | ✅ 有跡象 | 可繼續 |
| **營養表整列一框** | ❌ 過擬合都失敗 | **放棄，改回逐格** |

欄位與數值的關聯交給 `table_geometry.py` 的名次配對（依欄分群、各欄由上而下
排序、第 n 個對第 n 個）——它對傾斜／透視／曲面免疫，c28 實測從 0 到 15/16。
**det 負責框準，程式負責配對**，各做各自擅長的。

若要繼續 det 微調，依這輪的規模推估需要 **25–30 張訓練 + 8–10 張驗證**
（現為 7 + 2）。目標鎖定「深色底＋反光膜的縱向誤合併」那類，
因為那是唯一「資訊充足但模型判斷錯」的乾淨標的。

相關檔案：`configs/det_foodlabel_ft.yml`、`make_det_dataset.py`、
`prelabel_det.py`、`output/det_foodlabel_ft/`、preset `v6_det_ft`。

| **base（無前處理）** | 630 | 65 | 60 | 33 | 0.73s |

| unsharp（銳化） | 629 | 68 | 68 | 22 | 0.81s |

### 沒有一種帶來有意義的改善

最好的 `gray` 只比 base 多 4 格，而本專案的雜訊底線是 ±4–5

**結論是這條路走不通，不是還沒調對參數。**

### 兩個災難，原因不同

- **binarize −116**：如預期。PP-OCR 訓練用的是自然影像，二值化把輸入推出
  訓練分布。這是傳統 OCR 的標準前處理，對現代深度模型無效——
  **記在這裡是為了讓日後的人不必再試一次。**
- **glare −131**：**出乎預料，而且是全場最差。** 原本推測抑制反光會幫到
  c58 那類（深色底白字＋收縮膜亮條紋），結果 `cv2.inpaint` 把過曝區補起來時
  **連白色的字一起抹掉了**——在深底白字的包裝上，文字本身就是高亮度區。
  這是「直覺與實測相反」的第三個案例（前兩個是 `use_doc_unwarping` 與
  「解析度愈高愈好」）。

### CLAHE 愈強愈糟

623 → 612，而且繁簡差異 33 → 44。提高局部對比同時放大了雜訊，讓 rec 更容易
認錯字。局部對比不是這批照片的瓶頸。

### 唯一實務上有價值的：灰階能省時間

準確度在雜訊內，但 **p50 從 0.73s 降到 0.60s（快 18%）**——少了兩個色彩通道
的處理。要部署到 Raspberry Pi 那類算力有限的環境時，這是免費的加速。

保留意見：這 58 案裡沒有「必須靠顏色分辨文字」的情況。若之後納入彩色底的
標示，灰階可能反而不利，屆時要重測。

## 2026-08-17 PaddleOCR-VL 1.6（GGUF，整頁餵）

端到端 VLM，直接吐閱讀順序的文字。會試它就是因為上面那條「最大失分在行序
／版面重建，而那段 fine-tune det/rec 都碰不到」。

跑法見 `run_vlm.py`（LM Studio 起 server，OpenAI 相容端點）。輸出格式對齊
`run_baseline.py`，所以 `score_ocr.py --preset=vlm_2048` 直接可比。

| 58 案合計 | PP-OCR v6_hires__boxth0.4 | PaddleOCR-VL 2048 |
|---|---|---|
| 成分沒讀到 | **65** | 109 |
| 營養漏欄（共 878 格） | **60** | 347 |

看合計會得到「VLM 比較差」，但那是被 4 個案例吃掉的。逐案比是 **VLM 少漏 14 案、
多漏 12 案、持平 31 案**，而多漏的那 12 案裡有 4 個是整段退化：

| 只算另外 54 案 | PP-OCR | PaddleOCR-VL |
|---|---|---|
| 成分沒讀到 | 36 | **21** |
| 營養漏欄 | **46** | 281 |

### 成分：VLM 確實補到了行序那一段

VLM 贏的案例幾乎都是巢狀配方的多行區塊——PP-OCR 依框的位置輸出時會被拆散的
那一類：c09 麻婆豆腐燴飯 5→0、c46 雙拼起司紅醬焗飯 5→1、c31 增雞蛋白餐 3→0、
c35 極饕麻醬涼麵 3→0、c37 爆蛋流心豬肉堡 6→5。

c38 科學麵轉正後可以看到它在做什麼：整段成分是一條連續的閱讀順序文字，
從「麵粉、精製棕櫚油(…)」一路到「麥芽糊精」，只錯 芝麻油→高麻油、
關華豆膠→閣華豆膠、薑→薯 三個字。PP-OCR 在同一張圖上字也都讀到了，
但散成 55 個框、要靠下游重排。

### 營養：不能用，而且是全面性的

281/878 不是集中在難案。c20、c33、c47、c48、c56、c57 這些 PP-OCR 一格都沒漏的
案例，VLM 是 16 格全漏——它讀完成分就跳過整張營養表，或把數字讀成別的。
即使有讀到的，小數點大量掉字（c38：4.2→42、8.9→3.9、720→72）。

**所以 `nutrition_solver.py` 那條線不要動。** 約束求解吃的是 PP-OCR 的數字，
換成 VLM 等於把輸入品質砍掉一半。

### 逐字準確度：VLM 明顯比較好，這才是重點

| 成分字串 CER 錯字 | PP-OCR | PaddleOCR-VL |
|---|---|---|
| 全部 57 案 | 2393 | **1862** |
| 扣掉 4 個崩潰案 | 1236 | **510** |

CER 在這個專案一向被當輔助指標，因為它對行序敏感而 PP-OCR 的行序本來就亂
（見上面 c38 那段：104 個「錯字」其實是排序造成的假象）。**那個扣分項正是
VLM 沒有的**——它直接吐閱讀順序，所以 CER 才會掉一半以上。

繁簡反而變差（33 → 75 字），但那是字集問題，OpenCC 後處理即可，不是辨識錯誤。

### 4 個崩潰案：不是截斷，也不是解析度

c57/c58/c59（三款泡麵，4284×5712，成分是極小的密排小字）與 c24。
症狀是鎖進迴圈重複同一段直到吃滿 max_tokens。

**把 max_tokens 從 2048 放寬到 6144 反而更糟**（沒讀到 109 → 114，見
`out/vlm_2048_long/`）——多出來的 token 全進了迴圈。c58 吐出一條 8596 字的
單行，內容是「调味品、食品、调味品、食品…」重複到底。所以不是空間不夠，
是模型在那種輸入上根本沒在讀。

`repeat_penalty` 修不乾淨：同一張 c38，rot=90 時 1.15 正常收尾、1.10 爆迴圈；
rot=270 時完全相反。這不是還沒調到最佳值。目前用 1.15 加上事後
`dedup_lines()`（同一行出現第 3 次以上才砍，雙欄表本來就有兩行「0公克」）。

**「字太小」的推測已排除。** 字距取「框長邊 ÷ 該行字數」、行寬取框短邊
（別用短邊中位數當字高，有些框跨了兩欄，會高估）：

| 成分區字距 | 原圖 | VLM（整頁→2048） | PP-OCR rec（行裁圖→48px 高） |
|---|---|---|---|
| c58 | 93px | 33px | 18px |
| c57 | 77px | 27px | 14px |
| c59 | 86px | 31px | 30px |
| c37（沒崩，還贏 PP-OCR） | 48px | **24px** | 16px |

PP-OCR 的 rec 拿到的是「從**原圖**裁出該行、拉成 48px 高」
（`rec_image_shape=[3,48,320]`，見
`paddlex/inference/pipelines/ocr/pipeline.py:411`）。
**VLM 每個字拿到的像素比 PP-OCR rec 還多**，而且崩掉的 c58（33px）比沒崩的
c37（24px）字還大。解析度不是變因。

模型本身也不是量化壞掉的：GGUF `general.file_type=32`（BF16），沒量化。
它就只是小——467M 的 LLM ＋ 439M 的視覺編碼器。

### 這三案四個方向全滅，而且會「安靜地」壞掉

把 c57/c58/c59 的 0/90/180/270 度各跑一次，12 次沒有一次是對的。危險的是
**其中有幾次收尾很乾淨**——c58 rot=0 吐出 11 行、`finish=stop`、格式工整：

```
品名：抗糖道白大球香風味拉縫          ← 正解是「拉麵道日式豚骨風味」
1. 鹽粉、精製老餅油含糖油、糖及化劑或含藥物生食雞、粘稠與鴨鳩等食材
2. 調味物包：肥厚乳粉、食鹽、乳維、滷肉飯味水蜜肉抽牛奶水、糖油、鋪料精
```

這不是認錯字，是**通篇編造**——長度合理、句法像成分表、看起來完全正常。
c59 rot=90 吐「470」兩個字就停，c57 rot=180 吐「鵲樓蟻螢」。

**爆迴圈至少看得出來壞了，這種看不出來。** 而 VLM 沒有 rec 那種逐字信心值
可以拿來擋，下游無從判斷該不該信。

那張圖的條件：深藍底白字、包收縮膜且有整條反光、杯身是圓的字會扭曲、
直排密字。同一張 c58 也是前面「反光抑制」前處理實測全場最差（−131）的那案。

### 兩個踩到的坑

- **LM Studio 要看到 `mmproj-*.gguf` 前綴才會配對。** HuggingFace 上那份叫
  `PaddleOCR-VL-1.6-GGUF-mmproj.gguf`，mmproj 在字尾，LM Studio 會當成兩個
  獨立模型；送圖進去回 `does not support image inputs`。改名即可。
- **側躺的圖要先轉正。** 這批圖 EXIF orientation 全是 1 或 None，照片是真的
  存成側躺的。VLM 沒有 PP-OCR 的 textline orientation 那段，不轉正會掉字
  （c38 不轉正只讀到營養表，成分整段沒出來）。`vlm_orient.py` 從既有的
  PP-OCR 框長寬比判斷要不要轉（67 張裡 7 張要），方向分不出來所以 90/270
  都跑、取去重後漢字多的那個。

### 為什麼合計輸：差在失效模式，不是差在讀字

**它讀字比 PP-OCR 準**（CER 510 vs 1236），**成分逐項也贏**（21 vs 36）。
合計會輸是因為它的失敗是**無界的**，而 PP-OCR 的失敗是有界的：

- **PP-OCR 結構上不會漏區塊也不會跳針。** det 框出來的每一框都會進 rec，
  rec 是在固定寬度的特徵圖上逐格輸出——最壞情況是那一行認錯字，而且附帶
  信心值。它沒有「整張營養表不讀」或「同一句重複兩千次」這種行為。
- **VLM 要自己決定讀什麼、讀到哪停。** 三種 PP-OCR 不會有的失效：整段迴圈
  （c57/c58/c59）、整個區塊跳過（c20/c33/c47/c48/c56/c57 的營養表 16 格全漏，
  而這些案例 PP-OCR 一格都沒漏）、以及沒有信心值可以拿來擋。

109 個沒讀到裡有 88 個來自 4 個案例；347 個營養漏欄裡有一大半來自「整張表
沒讀」。這不是準確度問題，是穩定度問題。

**比較本身也不對等，要記住。** `v6_hires__boxth0.4` 是掃了十幾組 preset 選出來的
贏家，VLM 這邊等於只跑了一組設定。VLM 的數字是初測，PP-OCR 的數字是調過的。

### 結論

**不要拿它換掉 PP-OCR，但成分那一段值得接。** 它補的正好是上面標為「最大失分
項」的行序問題，而它壞掉的營養數值那段，PP-OCR 加約束求解已經在做而且做得好。

未驗證的下一步：PaddleOCR-VL 的官方管線是 PP-DocLayoutV2 先切版面、再逐塊
餵 VL，整頁餵是 off-label 用法。用既有的 PP-OCR 框當版面階段、把成分區裁出來
單獨餵，除了對齊官方用法，也把輸出長度切短——那正是三個崩潰案的共通點。
**還沒做，別當成已知結論。**

## 2026-08-18 區域切割（`region_crop.py`）

在讀之前先用既有的 PP-OCR 框把「營養表」與「成分區」切出來，之後才決定各自
送給誰讀。動機有三個：整張餵任何讀取器都沒有輸出長度上限（VLM 三個杯麵案
就是這樣爆的）、送出去的資料量大（正式管線平均每案 1.9MB／p50 11.3s）、
以及這兩塊該用不同方法讀（數值可算術驗證，成分不行）。

**這一步是單點故障，所以它有自己的指標。** 端到端 F1 看不出是哪一層在漏。

### 指標怎麼定的（不需要新標註）

拿現成的 GT 當尺，比較「整張圖的 OCR 文字」與「只看裁切框內的 OCR 文字」：

- 成分：GT 的成分項有幾個還找得到 → **因裁切而掉了幾項**
- 營養：GT 的數值有幾格還找得到 → **因裁切而掉了幾格**

分母是「整張圖讀得到的」而不是 GT 全部，因為 OCR 本來就沒讀到的不該算在
裁切頭上。這樣量到的純粹是這一層的損失。

### 結果

| | 成分區 | 營養區 |
|---|---|---|
| 57 案中切出來 | **57** | 52 |
| 裁切後保留 | **719 / 724 項** | 756 / 818 格 |
| 平均佔文字範圍 | 58% | **22%** |

營養區只佔 22%——送去給模型讀的資料量大致按這個比例降。

### 走過的兩個彎路

**先分群再分類會失敗。** 第一版是「用鄰近度把文字行分群 → 每群看關鍵字判類」。
包裝上營養表就緊貼著成分段，鄰近度分不開：c38 是 55 行併成 48 行的一整塊，
整塊判成營養表，**57 案只切出 9 案的成分區**。

**種子詞不能收「糖」「鈉」「公克」。** 成分表裡的「蔗糖」「多磷酸鈉」會讓
整個成分區被判成營養表。只收不會出現在成分表裡的：熱量、蛋白質、飽和脂肪、
反式脂肪、碳水化合物、每一份量、本包裝含、營養標示，湊滿 3 種才算。

### 能用的作法：先抓營養表，扣掉，剩下的長行才是成分

1. **營養表**用種子詞當錨，再往外吸收數值格。**成長必須限制只吸收「短行且
   含數字或單位」的**——不限制會雪崩：c40 實測整片成分行被營養表吞掉，
   成分區只剩 3 行（40 項掉到 9 項）。
2. **扣掉營養表**之後，用「行長」挑成分：成分是橫貫整個標示面的長行，
   營養表是一格一格的短行。實測中位數 c38 853 vs 136、c09 1782 vs 274、
   c44 2260 vs 335。門檻取該圖行長 90 百分位的 0.45 倍。
3. 長行再分群，取含「成分／原料／內容物」錨點的那些塊的聯集
   （成分常分成麵包／油包／粉包好幾團，要全收）。沒錨點才退而取字最多的塊。

`c58` 是行長訊號的反例（營養表整列被框成一長條，2400 vs 2171 分不開），
所以營養表仍然要先用種子詞抓出來扣掉，不能只靠長度。

### 還沒解決的

- **營養區 5 案沒切出來**：c58/c59（側躺杯麵，種子詞本身就沒被 OCR 讀到）、
  c04、c11/c12（御飯糰，整張只有 1 格營養數值）
- **c48 切出來但位置錯**（16 格全掉）
- **成分區 c19 掉 4 項、c44 掉 1 項**

## 2026-08-18 官方 PaddleOCRVL 管線（`run_vlpipe.py`）

paddleocr 3.7.0 內建 `PaddleOCRVL`，就是「版面偵測 → 逐塊送 VL」的官方管線。
與 `run_vlm.py` 用**同一個 GGUF、同一個 LM Studio server**，差別只有中間多了
PP-DocLayoutV3 的版面階段，所以差異可直接歸因於版面階段。

接法：不必裝 torch／transformers。`vl_rec_backend="llama-cpp-server"` 指向
LM Studio 的 `/v1`，只需要 `pip install "openai>=1.63"`（genai-client plugin）。
`use_doc_orientation_classify=True` 直接取代手刻的 `vlm_orient.py`。

### 三方並排（58 案）

| | PP-OCR | VLM 整頁 | **VL 官方管線** |
|---|---|---|---|
| 成分沒讀到 | **65** | 109 | 137 |
| 營養漏欄（878 格） | **60** | 347 | **172** |
| 成分 CER 錯字 | 2393 | **1862** | 1996 |

（管線有 2 案因 LM Studio 回 `Content-only format` 而失敗；扣掉後為
130 / 156 / 1964。）

### 版面階段把營養砍半，卻讓成分變差

**營養 347 → 156，砍掉一半以上。** 版面階段是真的有用。

**但成分 109 → 130，反而退步。** 失效模式換了一種：整頁餵是解碼器退化，
官方管線是**版面偵測整塊漏掉**——而漏掉的區塊是靜默且全損的。
c52 整張只判出 1 個 `image` 塊、c59 只有 3 塊，那些案的成分等於一個字都沒讀。

### 指標沒抓到的那件事：輸出是**有結構的**

c38 的營養表是以 HTML `<table>` 出來的，行列對齊正確：

```
蛋白質    4.2公克   10.5公克     ← 全對
飽和脂肪  4.4公克   10.9公克     ← 全對
碳水化合物 24.6公克  61.4公克     ← 全對
```

對照整頁餵的同一張圖：4.2→42、8.9→3.9、720→72。

`score_ocr.py` 的營養指標問的是「這個數字有沒有出現在文字裡」，量不到
「每份／每 100 克有沒有配對正確」。**而配對正確正是 `nutrition_solver.py`
現在要用約束去重建的東西。** 所以 60 vs 156 這個比較低估了管線的價值——
PP-OCR 給的是散落的數字，管線給的是表格。

### 我猜錯的一件事：官方版面偵測抓營養表不如手刻的種子詞

原本推測「`LayoutDetection` 的 `table` 類別可以換掉 `region_crop.py` 的種子詞法」。
實測相反：

| 抓到營養表 | 命中 |
|---|---|
| `region_crop.py` 種子詞 | **52 / 57** |
| 官方 PP-DocLayoutV3 的 `table` | 43 / 58 |

PP-DocLayout 是在文件（論文、報表、報紙）上訓練的，彎曲塑膠包裝離那個分布很遠。
3 案整張被判成 `image`：c05（非食品，這個判對了）、c52、c58。

### 結論

**版面階段要留，但不要用官方的版面模型。** 最好的組合是
`region_crop.py`（PP-OCR 框＋領域關鍵字，營養表 52/57）負責切，
再把裁切結果送給讀取器——而不是讓 PP-DocLayoutV3 決定哪裡有字。

## 2026-08-18 混合版：region_crop 的框 ＋ VL（`run_vlcrop.py`）

把版面階段換成 `region_crop.py`（PP-OCR 框＋領域關鍵字），保留官方管線的
逐區提示詞——文字區 `OCR:`、營養表 `Table Recognition:`
（見 `paddlex/inference/pipelines/paddleocr_vl/pipeline.py:308-313`）。
方向逐區判而不是逐頁判：包裝上常常營養表橫排、成分直排。

### 四方並排（58 案）

| | PP-OCR | VLM 整頁 | 官方版面 | **region_crop 混合** |
|---|---|---|---|---|
| 成分沒讀到 | **65** | 109 | 137 | 85 |
| 營養漏欄（878 格） | **60** | 347 | 172 | 98 |
| 成分 CER 錯字 | 2393 | 1862 | 1996 | **1528** |

**CER 1528 是四組最好的**，比 PP-OCR 的 2393 少掉近四成。逐案比是
少漏 15 案、多漏 9 案、持平 34 案。

**region_crop 混合版**耗時 561s／58 案 ≈ 9.7s 每案（VL 逐區重讀，每案要跑多次 VL 推論）。
⚠ 這是**這個混合版**的數字，不是 PP-OCR 管線的——PP-OCR 是 0.77s/案，快 13 倍。
見開頭的〈讀取器命名對照〉。與 Gemini（p50 13.5s）同級，但在本機、免費。

### 剩下的失分集中在 5 案

| 只算另外 53 案 | PP-OCR | 混合版 |
|---|---|---|
| 成分沒讀到 | 39 | **9** |
| 營養漏欄 | **42** | 62 |

成分 39 → 9。**這是整串實驗第一次出現 VL 在主要指標上明顯贏過 PP-OCR。**

崩的 5 案與原因：

- **c58／c59**（+20／+14）：仍然 `finish=length`。成分區單獨裁出來還是太長
  （GT 596／547 字，全套最長），輸出長度沒被壓夠。標示本身有 `1.` `2.` `3.` `4.`
  的分段編號，下一步應該照那個再切一層。
- **c38**（+9）：**裁切反而變差**。原圖只有 1391×1570，裁切不會提高字級
  （maxside 2048 不會放大），但少了上下文。裁切對大圖有利、對小圖可能有害——
  這條要加尺寸門檻。
- c19（+4）、c30（+3）：同上，都是小圖。

### 結論

版面階段用 `region_crop.py`、提示詞用官方那套分區的，是目前最好的 VL 組合，
而且逐字準確度已經贏過 PP-OCR。營養仍略輸（98 vs 60），但那個指標量不到
「每份／每100克配對正確」——混合版拿到的是 HTML 表格，PP-OCR 是散落的數字。

## 2026-08-18 抽取層的天花板與缺口分解（`bench_ceiling.py`）

`score_ocr.py` 說 OCR 把 91.8% 的成分讀進文字裡，`bench_ingredients.py` 說
只有 62.5% 進得了清單。中間掉的三十個百分點，是「行序／字錯」還是「切分」？
兩者的修法完全不同——前者是工程（座標排序、更好的讀取器），後者要語言知識
（「多磷酸鈉」是一項、「食鹽、水」是兩項，幾何規則不可能知道）。

`bench_ceiling.py` 把 OCR 與行序的變因整個拿掉：直接餵 GT 的 `ingredients_raw`。

### 同一批抽取器、三種輸入

| 抽取器 | PP-OCR 文字 | **混合版文字** | 完美文字（天花板） |
|---|---|---|---|
| dict | 67.6% | **74.0%** | 83.5% |
| union | 66.2% | **75.7%** | — |
| segment | 66.0% | 75.4% | — |
| hybrid | 67.0% | 74.1% | 83.5% |
| filter | 61.0% | 66.5% | **88.9%** |

（`naive`／`bracket`／`segment`／`union` 在完美文字上只有 5–10%，那是測試假象
不是天花板：GT 的 `ingredients_raw` 沒有「成分：」開頭，這幾支靠 `HEAD` 定位
段落，找不到起點。要看天花板請看 `filter` 的 88.9%。）

### 缺口分成三段，大小量出來了

```
完美文字 + 現有規則        F1 88.9%   ← 規則本身就損失 11 點（切分，需要語言知識）
混合版文字 + 現有規則      F1 75.7%   ← 文字品質再損失 13 點
PP-OCR 文字 + 現有規則     F1 67.6%   ← 再損失 8 點
```

**最大的一段是文字品質與行序（21 點），不是切分（11 點）。**
而混合版已經把其中 8 點拿回來了（67.6 → 75.7，召回 62.5% → 73.9%）。

### 但量到添加物層就翻盤了（`sim_match_preset.py`）

既有結論已經踩過一次這個坑：清單層 F1 打平的兩個操作點，到添加物層是反過來的
（p_dict 70.2 vs p_boxsep 72.3）。所以清單層的 +8 點不能當結論。

| preset | 抽取器 | 召回 | 精確 | F1 |
|---|---|---|---|---|
| PP-OCR | boxsep | 59.7% | **84.6%** | **70.0%** |
| 混合版 | boxsep | **62.0%** | 77.7% | 69.0% |
| PP-OCR | dict | 52.7% | 87.2% | 65.7% |
| 混合版 | dict | 60.5% | 79.6% | 68.7% |

**最佳操作點上混合版沒有贏（69.0 vs 70.0）**：多 2.3 點召回，賠掉 6.9 點精確。

原因就是前面量到的失效模式：**VL 的錯誤是「格式良好」的。**
PP-OCR 讀錯會產生對不到任何添加物的垃圾碎片（所以精確度不受傷），
VL 讀錯會產生**看起來像真添加物名的中文**，直接變成假警示。
對食安 app 來說，這是比漏讀更危險的方向。

### 這證實了「順序無關指標低估混合版」的推論——但只到清單層

`score_ocr.py` 的成分逐項命中是刻意設計成順序無關的（理由見前文），
所以混合版在那把尺上只是打平（89.2% vs 91.8%）。但一換到**會用到順序的
下游指標**，差距立刻出現：F1 67.6% → 75.7%。

順帶一提，混合版的 F1 75.7% 高於 `bench_ingredients.py` 裡 Gemini 那條
（65.4%），但 Gemini 只有 47/57 案有預測、GT 基數不同，不可直接比。

### 添加物層漏掉的 52 個，掉在哪一層（`miss_additives.py`）

召回 59.7% 代表 129 個真值裡漏了 52 個。那個百分比問不出下一步，拆開才行：

| 層 | 個數 | 意思 |
|---|---|---|
| 影像／OCR | 18 | 那些字根本不在 OCR 文字裡 |
| 解析 | 13 | 字在文字裡，但沒被切成項目 |
| 比對 | 21 | 項目切出來了，但沒配到 DB |

**「比對」那 21 個其實多半也是切分問題。** c44 實測：抽取器吐出一個 **316 字**的
巨大項目（`高湯{水、酸白菜(…)、乳化劑(脂肪酸甘油酯…)…`），
`5'-次黃嘌呤核苷磷酸二鈉` 確實在裡面但只佔 3%，被比對規則的 60% 比例門檻擋掉。
而 GT 是把 `玉米糖膠`、`刺槐豆膠`、`5'-次黃嘌呤核苷磷酸二鈉` 分開列的。

所以真正的分佈是 **OCR 18 個、切分 34 個**——**三分之二的召回損失在切分**，
與 `bench_ceiling.py` 量到的「規則在完美文字上也只有 88.9%」互相印證。

> 寫這支時踩到的坑：添加物的鍵可能是「正式名； 別名」的合併字串，
> 拿整串去比對文字一定找不到。第一版因此把 `醋酸鈉` 四案誤判成「OCR 沒讀到」，
> 其實那三個字明明在文字裡。要逐個名稱形式分別判。

## 2026-08-18 讓 rec 在辨識時就用上添加物詞彙——逐字候選拿得到

`paddlex/inference/models/text_recognition/processors.py:296` 的
`preds.argmax(axis=-1)` 之前，`preds` 是**整個字表上的機率分佈**。
攔截 `CTCLabelDecode.__call__` 就拿得到，實測張量是 `(102, 18385)`
（時間步 × 字表）。跟 `table_geometry.py` 的情況一樣：資訊一直都在，被丟掉而已。

c38 一行的實測（`豆糖、醬油、麻油、關華豆膠、多磷酸鈉、抗氧化劑混合濃縮生育醇(含`）：

```
t= 49  碳=0.92  磷=0.05  炭=0.00     ← 輸出「多碳酸鈉」，正確的磷在第 2 候選
t= 30  關=0.58  关=0.19  blank=0.02
t= 56  鈉=0.64  钠=0.27  納=0.01
t= 72  劑=0.85  剂=0.10  刺=0.01
t= 85  縮=0.83  缩=0.10  blank=0.04
```

`多磷酸鈉` 在添加物庫裡、`多碳酸鈉` 不在——字典約束的解碼會選對。

### 兩個可做的，成本差很多

**1. 限制字表成純繁體（幾乎免費、零風險）。** 上面每一列的第二候選幾乎都是
同一個字的簡體（关／钠／剂／缩），模型是真的在兩者之間猶豫。
台灣的標示不會出現簡體，解碼時把簡體字位罩掉即可，
基準線那 227 字的繁簡差異可以直接消掉，而且不可能改錯——
它換掉的是同一個字的另一種寫法，不是另一個字。

**2. 字典約束解碼。** 用 top-k 做 beam search，候選字串必須能被
`data/ingredient_dict.json` 支持。

**這與已否決的「OCR 後修正」不是同一件事，差別在有沒有用到模型的信心。**
既有結論：把讀出的字串用編輯距離對到最近的字典詞 → 添加物層 F1 70.0→**53.0**，
因為「短名稱最容易讀錯，但改一個字就會落到另一個真的添加物上」。
那個做法是在**最終字串**上動刀，不知道模型對哪個字沒把握，所以會去改一個
本來讀對的字。約束解碼只在模型自己已經猶豫的位置（碳 0.92 / 磷 0.05）
做選擇，讀得很篤定的字它碰不到。這個差別決定了安全性。

### 但要先知道它的天花板在哪

這條路攻的是 `miss_additives.py` 裡「影像／OCR」那 **18 個**，
佔 52 個漏失的 35%。另外 34 個是切分問題，字典約束解碼碰不到。
**值得做，但不是最大的槓桿。**

（PP-OCR 時是 18／13／21）。

### 但營養解析換成 Vision 是**退步**（`nutrition_gv.py` / `bench_parse_gv.py`）

複製 `nutrition_pipeline.py` 的架構（全圖 ＋ 營養區裁切重讀，取聯集），
兩端都換成 Vision，版面階段用 `region_crop.py`（抓營養表 53/57）。
解析邏輯一行沒動，差異可歸因於讀取器。

| `fill` 解析器 | 正確 / 878 | 全對案例 |
|---|---|---|
| PP-OCR（現況） | **702（80.0%）** | **27** |
| PP-OCR 拿掉 table_html_text | 692（78.8%） | 22 |
| **Vision** | 588（67.0%） | 15 |

逐案：Vision 較好 9 案、**較差 30 案**、持平 18 案。而且差的那幾案是
PP-OCR 本來滿分的（c35／c20／c30／c44 都是 16/16 → 4–6）。

**先排除了 `table_html_text` 的因素**——把它從 PP-OCR 那組拿掉只掉 10 格
（702→692），不是 Vision 落後 104 格的原因。

### 原因：Vision 會把並排的兩欄黏成一行

c38 的實際輸出：

```
『粉、精製醬油(棕櫚油、抗氧化劑混合濃縮生育醇)、食鹽、水、味精、每一份量40公克
蔗糖、醬油、芝麻油、關華豆膠、多磷酸鈉、抗氧化劑混合濃縮生育醇(含本包裝含1份
```

成分那一行和營養表的表頭（`每一份量40公克`／`本包裝含1份`）被黏在一起——
它們在版面上是**並排的兩欄**，Vision 依整頁的文字流讀，跨欄接了起來。
解析器的「欄位名後面接數值」樣板一碰到這個就崩。

這正是既有結論早就記過的坑：「全域排序會把並排的兩欄交錯成『左一句右一句』，
而食品包裝正是多欄排版」。PP-OCR 逐框輸出反而保住了欄的邊界。

數值本身也較差：同一張圖 PP-OCR 讀出 `720毫克1800毫克`、`4.4公克 10.9公克`
（全對），Vision 是 `195大卡48卡`（488→48）、`4.4公克10.3公克`（10.9→10.3）。

### 結論：兩半要用不同的讀取器

| | 讀取器 | 證據 |
|---|---|---|
| **成分** | **Google Vision** | 沒讀到 34 vs 65；添加物層 F1 72.3 vs 70.0 |
| **營養** | **PP-OCR ＋ 幾何配對** | 702 vs 588 |

不是折衷，是結構決定的：**成分是一整段連續文字**，Vision 的整頁閱讀順序是優勢；
**營養是多欄表格**，Vision 跨欄黏行是災難，而 PP-OCR 的逐行框＋
`table_geometry.py` 的幾何配對正好對症。

`region_crop.py` 已經把兩個區域分開了，所以這個分流不需要額外的架構。

### 分流實作（`run_split.py`）：成分側的區域裁切是**沒有作用**的

把 Vision 的行用 `region_crop.py` 的成分區框濾一遍（濾掉 1341 行、留 2316 行），
再送進同一批抽取器。結果與**沒有裁切的 Vision 完全一樣**：

| 添加物層 | 召回 | 精確 | F1 |
|---|---|---|---|
| gvision + dict | 62.8% | 85.3% | 72.3% |
| **split + dict** | 62.8% | 85.3% | **72.3%** |
| gvision + boxsep | 65.1% | 80.8% | 72.1% |
| **split + boxsep** | 65.1% | 80.8% | **72.1%** |

原因：抽取器本來就有自己的 `HEAD`／`TAIL` 段落定位，已經在做同一件事——
用文字找出成分段的起訖。再加一層幾何裁切是重複的。

**所以分流的正確形狀比原本設想的更簡單**，少一個零件：

```
成分  →  Vision 全圖文字  →  現有抽取器          （不需要 region_crop）
營養  →  PP-OCR ＋ table_geometry ＋ solver      （完全不動）
```

`region_crop.py` 的價值是專屬於 VL 那條路的（用來限制輸出長度），
換成 Vision 之後就不需要了。

### 端到端結果

| | 現況（全 PP-OCR） | **分流** |
|---|---|---|
| 營養 `fill` | 702 / 878 | **702 / 878**（不動） |
| 成分添加物層 F1 | 70.0%（boxsep） | **72.1–72.3%** |
| 成分添加物層召回 | 59.7% | **65.1%**（boxsep） |

召回 59.7% → 65.1%，精確度 84.6% → 80.8%（boxsep）；
或選 dict 是召回 62.8%／精確 **85.3%**，兩項都優於現況。
成本是每張圖 1 個 Vision unit。


## 2026-08-18 切分模型的合成訓練資料（`synth_split.py`）

添加物層漏掉的 52 個裡，**34 個是切分失敗**（13 個整項沒切出來、21 個切成一大坨），
只有 18 個是 OCR 讀錯。而規則已到頂——`bench_ceiling.py` 量過，餵完美文字給現有
抽取器也只有 F1 88.9%。所以下一步是切分模型，而它需要 `(文字 → 清單)` 的配對資料。

**GT 的 57 案不能用**（汙染紅線），`predictions/` 是同一批案例也不能用。所以合成。

### 為什麼合成在這裡比 rec 那條有效

rec 合成要渲染出真實的反光／彎曲／字體，**有影像域差距**（上輪淨損 16 項）。
切分是純文字到純文字，沒有這個 gap。而且是**反向生成**：先造出清單再序列化成
字串，標籤是精確的而不是近似的。

詞彙沿用 `synth_corpus.py` 的 `ADDITIVES` ＋ `FOODS`（來自法規與添加物表、
與評估集無關），另補 `FUNCTIONAL` 功能類別詞——既有結論診斷出「劑」是上輪
rec 語料最大的缺口（測試集 99 次、語料 0 次），而巢狀複合成分幾乎都是
「功能類別詞(物質1、物質2…)」的形狀。

### 劣化條件對齊實際失敗模式

| 劣化 | 對應的真實失敗 |
|---|---|
| 丟頓號 | 「13 個」那一類（`關華豆膠多磷酸鈉` 黏成一串） |
| 括號讀錯／丟失 | 「21 個」那一類（c44 的 316 字一大坨） |
| 插入空白換行 | 跨框串接 |
| 字元混淆 | 用 `out/_dict_fixes.json` 實際記錄到的混淆對（碳/磷、納/鈉…） |

### 難度校準：用現有規則當標尺

合成資料最容易犯的錯是**太簡單**——練出來的模型到真實資料就失效。
所以用現有規則抽取器跑合成資料，對照它在真實與完美文字上的成績來調劣化率：

| 丟頓號 / 括號壞 | 召回 | 精確 | F1 |
|---|---|---|---|
| 0.12 / 0.25 | 69.3% | 78.3% | 73.5% |
| **0.17 / 0.33（採用）** | **61.4%** | **74.4%** | **67.3%** |
| 0.20 / 0.40 | 57.0% | 73.5% | 64.2% |
| 0.28 / 0.55 | 48.2% | 66.7% | 56.0% |
| **真實 PP-OCR 文字（目標）** | **62.5%** | **73.7%** | **67.6%** |

0.17 / 0.33 幾乎完全對上真實。產出：
`corpus/split_train.jsonl`（8000 筆）、`corpus/split_val.jsonl`（1000 筆）。

### 資料格式＝GT 的欄位形狀，零轉換

```json
{"input": "成份：香菇抽出物、麵條〔米酒、花椒…〕、甜味劑〔活性乳酸菌乳糖〕、芝麻…",
 "output": ["香菇抽出物", "麵條〔米酒、花椒…〕", "甜味劑〔活性乳酸菌、乳糖〕", "芝麻"]}
```

即 `ingredients_raw` → `ingredients_list`。

**安全性質**：正規化後的輸出字元必須是輸入字元的子集（`S.normalize` 會去標點，
所以模型補回頓號、統一括號全半形都不算違規）。這可以機械檢查——
模型只可能**切錯**（碎片配不到添加物，下游無害），不可能像 VL 那樣**編造**。

### 驗收標準（先訂好，不然會白做）

- 清單層：要贏過規則的天花板 **F1 88.9%**（`bench_ceiling.py`）
- 驗收層：`sim_match_preset.py` 的添加物層，現況最好是 **70.0%**（PP-OCR+boxsep）
- **精確度是約束不是目標**：掉到 80% 以下就是在製造假添加物警示

### 還沒解決的：那 21 個仍卡在慣例

GT 對巢狀複合成分的處理不一致——91 個複合項裡，**52 個內部成分也被單列、
39 個沒有**。`調味劑(A、B、C)` 到底算 1 項還是 3 項，現在正解有兩種答案。
合成資料目前是「整團保留成一項」，若決定改成展開，`--p-nested` 那段要重生。
**這個決定不做，模型會學到互相矛盾的示範。**


## 2026-08-18 切分模型：規格、資料、訓練

規格與驗收標準見 **`SPEC_split_model.md`**（含三個待決事項）。這裡只記過程中的教訓。

### 放棄了「先跑 LLM few-shot 基線」這一步

原本的計畫是先用本地 Qwen3.5-9B few-shot 跑一次，確認「模型有沒有用」再決定
要不要訓練。**這個順序算錯了成本**：

| | 實測 |
|---|---|
| 9B few-shot 基線 | 4.5 tok/s → 57 案要 **3–9 小時** |
| 訓練 0.1B BIO 標註器 | 8000 筆、4060 上**數分鐘** |

「便宜的檢查」比它要擋掉的訓練還貴，那就沒有意義。換 `--parallel=1`、
縮 context 都沒有改善——9B（6.1GB）在 8GB 的 4060 上就是塞不下。

附帶一個踩到的坑：Qwen3.5 預設開 thinking，推理走 `reasoning_content`、
答案走 `content`。`max_tokens` 給 150 時 content 是空的——**不是模型壞掉，
是推理把額度吃光了**。

### 合成資料：邊界要在生成時記錄，不要事後對齊

第一版是「劣化整串 → 用項目文字回去 input 裡找位置」，**55% 的樣本對不上**。
原因是字元混淆改了 input（`多磷酸鈉`→`多碳酸鈉`），項目文字自然找不到。

而且方向本來就錯了：**正確的標籤該來自劣化後的字串**。模型輸出的是輸入的片段，
讀錯的字應該原樣輸出，修字是 OCR 那一層的事。

改成 `synth_split.py` 在序列化時就記錄每項的起始位置（`boundaries` 欄位），
刪字元時左移、插字元時右移。零丟棄、完全精確。

### 模型選擇：`ckiplab/bert-base-chinese-ws`

不是 base，是**斷詞**的 checkpoint。中文斷詞與本任務結構完全相同——都是逐字
二元邊界預測、都是繁體中文。從已經會找中文邊界的模型起步，比從 base 收斂快。

不用 seq2seq 的理由：這個任務的輸出等於「輸入 ＋ 邊界標記」，沒有一個字是新的。
逐字分類**結構上不可能編造**，而 seq2seq 可以。既有結論已經踩過
「格式良好的錯誤比隨機碎片更危險」（見 PaddleOCR-VL 段）。

長序列用滑動視窗（512 窗、384 步、重疊 128），合併時**取視窗中央**的預測——
邊緣上下文不完整。不處理的話最難的 c57/c58/c59 會壞掉。

### 第一輪訓練結果（2026-08-18）

`ckiplab/bert-base-chinese-ws` fine-tune，8000 筆合成資料、3 epoch、
RTX 4060 上 **6 分鐘**。

| 添加物層（驗收指標） | 召回 | 精確 | F1 |
|---|---|---|---|
| PP-OCR + boxsep（基準） | 59.7% | **84.6%** | 70.0% |
| **BERT 切分模型** | **64.3%** | 82.2% | **72.2%** |
| （參照）Google Vision + dict | 62.8% | 85.3% | 72.3% |

**兩項驗收都過**：F1 72.2% > 70.0%，精確度 82.2% ≥ 80%。

而且 **72.2% 與 Google Vision 的 72.3% 實質打平**——用的是本地 PP-OCR 的文字
加一個 0.1B 的模型，沒有雲端。

### 三個要記住的細節

**1. 合成驗證集的 boundary F1 是 0.9999，這個數字沒有意義。**
與 rec fine-tune 那輪一模一樣的飽和模式（README 上面那段：「合成 val acc
在 epoch 10 就飽和到 ~1.0，best_accuracy 完全失效」）。
真實的成績只能看添加物層。

**2. 清單層反而變差**（F1 60.0% vs 規則 67.6%，精確度只有 52.3%）——模型會過度切分。
但那些碎片配不到添加物，所以到添加物層不但沒有傷害，還多換到 4.6 點召回。
**又一次驗證「中間層指標不能拿來做產品決策」**：只看清單層會誤判這輪是失敗的。

**3. 評分方式踩過一次坑。** `sim_match_preset.py` 會在 preset 的文字上**再跑一次
抽取器**——那對 OCR 輸出是對的，對切分模型的輸出是錯的（模型吐的已經是最終清單，
再抽一次會毀掉，實測 F1 掉到 11.6%）。所以另外寫了 `score_items.py` 直接比對。

### 剩下的雜訊來自段落定位，不是模型

c38 的輸出裡混著 `採食品`、`輻照殺菌處理`、`桐址：www.unl-president.com.tw`——
那些是 `p_union` 定位出來的成分段本來就含的雜訊（範圍 A1 的設計：段落定位交給規則）。
模型只負責切，切到雜訊也只能照切。若改成 **SPEC 待決事項 A 的 A2**
（模型同時做段落定位），這部分有機會改善，但合成資料要重生。

> 這是**第一輪、預設超參數、沒有調過**。epoch / 學習率 / 邊界門檻（現在 0.5）
> 都還沒掃過。

## 2026-08-18 參數搜尋與過擬合檢查（`tune_split.py` / `boot_compare.py`）

要調參，先問「這個測試集調得動嗎」。答案是**調不動，而且今天好幾個結論都站不住**。

### 添加物層的雜訊比想像大得多

`tune_split.py noise`：隨機切半 200 次、同一組參數，F1 的散布是

```
中位 72.2%   標準差 5.1 點   範圍 53.3–86.8%
```

而我們在追的效果只有 2 點級別。

### 配對 bootstrap：今天的三個「勝負」全都跨過 0

非配對的散布會混進案例難度的變異。正確的問法是「**差距**的分布」——
對案例重抽 5000 次，看差距的信賴區間（`boot_compare.py`）：

| 比較 | 差距 | 95% 信賴區間 | 判定 |
|---|---|---|---|
| BERT 切分 vs PP-OCR | +2.2 點 | **−3.7 ～ +7.9** | 跨 0，**不成立** |
| Google Vision vs PP-OCR | +2.3 點 | **−3.7 ～ +8.8** | 跨 0，**不成立** |
| region_crop 混合 vs PP-OCR | −1.0 點 | −11.2 ～ +7.7 | 跨 0 |

**所以今天報的「Vision 在添加物層贏」與「切分模型兩項驗收都過」，
在統計上都不能宣稱。** F1 確實比較高，但用 57 案（129 個添加物真值）分辨不出
那是真的增益還是抽樣運氣。

### 參數本身幾乎不重要，主導項是案例難度

固定切半（`case_id` 雜湊，可重現）：A 31 案、B 26 案。

| | 數值 |
|---|---|
| best_A 門檻 0.625 → 在 A | F1 80.7% |
| 同一門檻 → 在沒看過的 B | **F1 63.6%** |
| **過擬合量**（B 上直接選最好 vs 用 A 選的） | **0.6 點** |
| 門檻對全 57 案的貢獻（0.5 → 0.625） | **0.3 點** |

**過擬合量只有 0.6 點——因為根本沒有東西可以過擬合。**
門檻換來換去只值 0.3 點，而 A 半組與 B 半組的難度差了 **17 點**。
案例抽樣的變異壓過一切參數效果。

（另一個症狀：B 半組在**所有**門檻下精確度都低於 80% 的約束，A 半組則有 85.7%。
26 案的樣本量撐不起這種約束。）

### 結論：不要調參，去擴充測試集

以目前的樣本量，任何小於約 8 點的改動都無法驗證。可做的事只有兩件：

1. **擴充測試集**——把添加物真值從 129 個拉高。這是唯一能提高判別力的辦法，
   而且它同時讓今天所有「差 2 點」的比較變得可判定。
2. **只做效果夠大的改動**——小於 8 點的優化在這個測試集上是量不出來的，
   投入前先估效果量。

**這也回答了「怎麼避免過擬合」：現階段不是靠更聰明的搜尋演算法，
是不要在這個樣本量上搜尋。** 已經量到的過擬合量（0.6 點）遠小於
抽樣變異（±5 點以上），所以問題不在方法，在資料量。

### 門檻掃描：沒有任何操作點兩個指標同時贏

| 門檻 | 清單 F1 | 清單精確 | 添加物 F1 | 添加物召回 | 添加物精確 |
|---|---|---|---|---|---|
| 0.500 | 59.3 | 51.2 | **72.2** | 64.3 | 82.2 |
| 0.900 | 61.9 | 56.1 | 71.4 | 62.8 | 82.7 |
| 0.997 | 64.5 | 65.1 | 69.4 | 59.7 | 82.8 |
| **基準 PP-OCR + boxsep** | **66.7** | 65.6 | **70.0** | 59.7 | 84.6 |

清單層最好 64.5（仍低於基準 66.7），而該門檻下添加物層掉到 69.4（也低於基準）。
**模型是在做取捨，不是在改善。**

而且清單層的劣化是**可判定的**：配對 bootstrap 差距 −6.7 點、95% CI −11.3 ～ −2.0，
不跨 0。相對地添加物層的 +2.2 點 CI 跨 0。
**結論是「有證據說它讓清單變差，沒有證據說它讓下游變好」。**

### 診斷：對齊了總體難度，沒對齊失效分布

合成資料的校準只比對了**總體 F1**（67.3 vs 真實 67.6），那是必要但不充分的。
模型過度切分，表示它學到的邊界模式在真實 OCR 文字上不成立——
合成的「丟頓號」位置分布與真實的不一樣。

**教訓：合成資料要對齊的是失效分布，不只是總分。**

### 這一輪的結論

以現有測試集，這個模型**不能宣稱有效**，而且沒有操作點能同時改善兩個指標。
但真正的阻塞是量測而不是模型——添加物層（129 個真值）分辨不出 8 點以下的差異，
清單層雖有解析度卻對「過度切分」有已知偏見
（見上面 p_dict / p_boxsep 那個先例）。

**模型本身留著**（訓練 6 分鐘、推論 11ms/案，成本可忽略），
等測試集擴充後可以幾分鐘內重新評估。

### 為什麼營養表有效、成分區無效

**裁切放大提升的是 det 的偵測能力，不是 rec 的辨識能力。**

- rec 是從**原圖**裁出每一行、再拉成 48px 高（`rec_image_shape=[3,48,320]`）。
  把區域放大 2.5 倍再送進去，rec 拿到的是**內插出來的像素，不是更多資訊**。
- 營養表那次的增益來自 det：小格子的數字太小，det 在整張圖上偵測不到，
  放大後才框得到。
- 成分區沒有這個問題——`gap_vs_vision.py` 已經量過 **det 漏 0 項**

**這個結果在跑之前就該預料到。** 既有的量測已經指出失效在 rec，

原因是比例錯了：官方的 1:1:1 是 **真實:合成:通用**，通用佔三分之一。
但 `train_raw/` 是空的、沒有真實那一份，做成合成:通用 = 1:1
等於**通用佔了一半**。維基的字元分布離標示太遠（2423 種字 vs 食品語料 505 種），

### 量測方法的兩件事

**難度校準**：量到合成圖對未微調 rec 的信心中位 0.974、只有 16% 低於 0.9，
而真實行裁圖是 0.863 / 58%——**合成明顯太簡單**。加了 `--deg-scale` 掃強度，
但機率乘上去在 36% 就飽和；`lowres` 的下限 15px 是既有實測定的
（11px 時連未微調模型都吐空字串，那是「壞」不是「難」）。
**剩下的落差不在強度而在種類**——真實的低信心來自背景紋理、真實反光、曲面，
純色平面背景模擬不出來。要補只能用真實底圖合成（`train_raw/` 仍是空的）。

**驗收用筆數**：那 18 個指名的、因 OCR 而漏掉的添加物，
未微調讀到 1 個、v2 ep4 讀到 2 個。**rec fine-tune 沒有解決它要解決的問題。**

最好的 v2 ep4 是個取捨——成分逐字準了（+19、繁簡歸零），
代價是營養漏 65 → 90。那不是可以上線的交換。

還缺的是 1:1:1 的第一個 1（真實裁圖），但那要收新照片
（不能用評估集），而且以添加物層 ±6 點的判別力，做完也證明不了。

### 為什麼要三版才對：OpenCC 不能直接當「是不是簡體」的判準

**v1 用 `s2t` 判定**，實測造成破壞：

```
台→合 ×7    里→男 ×5    群→郡 ×3    热→熟 ×2    内→肉 ×2    吃→屹 ×2
```

遮掉 `台` 之後 argmax 落到第二候選 `合`，「台灣」變成「合灣」。
指標上看不出來（CER −3、完全命中 +1），因為修對的和弄壞的互相抵銷——
**「數字沒動」不等於「沒有傷害」，一定要逐字 diff。**

**修正靠三個判準，都有依據，不必手寫黑名單：**

1. **`STCharacters.txt` 是一對多的，候選清單含不含自己就是答案**
   （`台→臺 檯 颱 台` 含自己 → 合法繁體，不遮；`纳→納` 不含 → 遮）。
   全字表 18385 個字位裡，這樣的字有 170 個。
2. **用 `s2tw` 不用 `s2t`**。s2t 是港式標準，會把台灣標準字判成簡體：
   `s2t: 群→羣、吃→喫`，`s2tw: 群→群、吃→吃`。
3. **`t2s(c) == c` 才算簡體**。s2tw 也會把**繁體異體字**轉成台灣標準字，
   那不是簡體：`s2tw(喫)=吃`，於是 `喫` 被誤遮，
   **「純喫茶」變成「純噢茶」**——統一的產品名，v2 實測踩到。

### 這件事的實際價值已經被 Vision 稀釋了

當初提這個是為了讓 PP-OCR 讀成分讀得更準。但分流之後成分走 Vision
（它的繁簡差異本來就只有 7），PP-OCR 只負責營養表——那裡是數字和固定欄位名，
繁簡差異本來就少。**所以這個改動現在的價值主要在離線後備路徑**，
以及用 PP-OCR 文字交叉驗證 Vision 輸出時。零風險、零成本，做了不虧，
但不要期待它推動主要指標。

## 2026-08-18 用 Vision 當標尺定位 PP-OCR 的缺口（`gap_vs_vision.py`）

**Vision 是參照組不是元件。** 它讀到而 PP-OCR 沒讀到的成分，就是 PP-OCR
可改善的上限；而「該修哪一段」取決於失分在 det 還是 rec——這個區分沒有參照組
就做不出來，以前只能說「這項沒讀到」，不知道是沒看到還是看錯。

判法：取 Vision 讀到該成分那幾行的外接框，看 PP-OCR 有沒有框與它重疊。
巢狀配方橫跨很多行，整串比對找不到，所以逐步退到用前綴定位——
只要知道「從哪裡開始」就足以判斷 det 有沒有框到。

### 結果：39 項差距，det 沒框到的是 **0 項**

| | 項數 |
|---|---|
| rec 認錯字（有框、位置對得上，字讀錯） | **19** |
| **det 沒框到** | **0** |
| 定位不到（我的定位邏輯接不起來的長巢狀項目） | 20 |

**重疊門檻從 0.05 掃到 0.7，三個數字完全不動**——那 19 項全部都有 PP-OCR 的框
覆蓋超過 70% 的區域。這不是門檻調出來的結論。

這把既有基準線裡「det 沒有明顯在漏（逐行檢視最差案例，信心 0.83–0.94）」
從肉眼抽查換成了數字，也解釋了為什麼 det fine-tune 會失敗——**det 本來就沒在漏。**

### 所以要 tune 的是 rec，不是 det

而且最省的介入不是 fine-tune，是**字典約束解碼**：
`t=49 碳=0.92 磷=0.05`，`多磷酸鈉` 在添加物庫裡、`多碳酸鈉` 不在。
不需要任何訓練資料，用現成的 `data/ingredient_dict.json` 就能做。

## 2026-08-18 字典約束解碼（`dict_decode.py` / `run_baseline_dict.py`）

只在**模型自己沒把握**的位置，用成分字典挑一個能拼成真實詞彙的候選。
不需要訓練資料。全套只觸發 **15 筆替換**。

| | 完全命中 | 沒讀到 | CER | 繁簡 |
|---|---|---|---|---|
| 原本 | 630 | 65 | 2393 | 33 |
| 純繁體 | 631 | 65 | 2388 | 0 |
| **繁體＋字典** | **634** | 65 | **2381** | 0 |
| （參照）Vision | 672 | 34 | 1311 | 7 |

添加物層：boxsep 59.7/84.6/**70.0** → 60.5/83.0/**70.0**（召回 +0.8、精確 −1.6、
F1 不動）；dict 65.7 → 66.0。**淨效果接近零。**

### 五道保護，第五道是實測補的

1. top1 < 0.98 才考慮（模型猶豫過）——0.90 太緊，實際錯誤 `碳=0.92` 會被擋掉
2. 替代候選機率 >= 0.01
3. 替換後必須**剛好**拼出字典詞（完全相等，不是編輯距離）
4. 原本那段不能已經是字典詞
5. **鹽類字尾不動**：`酸根 + 鈉鉀鈣鎂銨鐵鋅銅…` 是規律構詞，字典收不齊所有組合。
   第一版實測把 **`琥珀酸鈉` 改成 `琥珀酸銅`**——因為 `琥珀酸鈉` 不在庫裡而
   `琥珀酸銅` 在。這正是既有結論警告的「改一個字就落到另一個真的添加物上」。
   加上這道之後 16 筆降為 15 筆，**剩下全部正確**（垂→華、百→白、碳→磷、
   已→己、醋→醯、針→鉀、含→合、礙→磷、納→鈉、澡→藻、沐→藻、假→胺）。

### 為什麼只有 15 筆：瓶頸是字典涵蓋率

`gap_vs_vision.py` 說可改善上限是 19 項，實際只吃到一小部分。原因是
`data/ingredient_dict.json` **只有添加物**——既有結論已量過它直接對上 GT 的
只有 84/789（10.6%）。`芝麻油→高麻油` 這種錯誤修不了，因為 `芝麻油` 根本不在庫裡。

所以這條路的天花板由字典決定，不是由方法決定。要再往上得換更廣的詞庫
（Open Food Facts 涵蓋 43%，但 ODbL 有 share-alike，公開發表前要確認可接受）。

### 結論：做了不虧，但別當成主力

零風險（15 筆逐筆檢查全對）、零資料成本、CER −12、完全命中 +4。
但**添加物層 F1 完全沒動**，而 PP-OCR 對 Vision 的差距還有 630→672、
沒讀到 65→34。這條路關不上那個缺口。

## 2026-08-19 整份 JSON 組裝（`emit_json.py`）——**出得來，但只有一半的欄位**

|---|---|---|---|
| `ingredients_list` | 56 | 57 | 有，添加物層 F1 70.0 |
| `ingredients_raw` | 56 | 57 | **重組的，不是逐字照抄** |
| `nutrition` / `nutrition_per_serving` | 57 | 53 / 57 | 有，878 格正確 701（80%） |
| `serving_size` | 53 | 57 | 正確 51/57 |

**結論：結構出得來，值只有一半。** 成分與營養兩層是這幾週在做的，接上去就有；
品名、品牌、製造商、過敏原、認證標章這五欄**從來沒有任何一層在處理**——
不是做得差，是零。要真的替換掉 Gemini，缺的是這五欄，不是再多幾點 F1。
其中 `allergy_warning`（49 案有）對下游的意義不亞於添加物。

### 組裝才看得見的兩件事

**一、`bench_parse` 的 80% 是純召回，沒有精確度。** `score_one` 對 GT 為 null 的格子
直接 `continue`（`bench_parse.py:63`），所以**硬填不會被扣分**。組成整份 JSON 後一數：
1026 格裡 GT 為 null 的有 148 格，我方填了 **125 格**。

主因是膳食纖維——**它不是法定必標欄位**，多數標示上根本沒這一列，
但序列對齊假設八欄俱全，會把碳水的數字塞進 `fiber`（57 案有 25 案兩者同值）。
加一條門檻（文字裡沒出現「膳食」就丟掉 fiber）：**硬填 125→27 格，
正確格只掉 1 格（702→701）**。丟掉的 4 格「真值」裡有 3 格本來就是錯的。
下游是拿去比對與示警的，假值比缺值貴得多。

**二、`servings_per_container` 靠算的比靠讀的多。** 直接讀「本包裝含 N 份」只有
10/57；補上「淨重 ÷ 每一份量」再取到整數或 .5（誤差 8% 內才採信）變成 35/57，
而且**給出的 35 個全對**。這是 `bench_parse._serving_size` 第 3 條路徑的反向，
同一條法規關係換一端已知。

### 誠實標記
輸出裡的 `_meta` 記三件事，讓下游能分辨值的來源：
`unfilled`（五個沒做的欄位）、`derived_cells`（44 格是用份量推導的、不是讀到的）、
`ingredients_raw_is_reconstructed`（原文是把切好的項目用頓號接回去的）。
`main.py` 寫入資料庫用的是 `COALESCE`，空字串會被當有效值蓋進去，
所以沒做的欄位一律 `null`／`[]`，不留空字串冒充。

**這支不讀 ground_truth。** 解析器簽章雖有 `gt` 參數，一律傳 `None`，
用到就會當場炸掉，不會靜默污染。

## 2026-08-20 PP-OCR 管線的實際耗時——**0.77s/案，不是 9.7s**

先前把 771 行那個「9.7s 每案」當成本管線的數字引用過，**那是錯的**：
771 行量的是 PaddleOCR-VL 的 `region_crop` 混合版（VLM 逐區重讀），
是另一套系統。`v6_hires__boxth0.4` ＋ `emit_json` 這條管線的耗時，
README 裡在此之前根本沒有紀錄。實測（GPU，58 案）：

| 階段 | 耗時 |
|---|---|
| 模型載入（一次性） | 13.0s |
| OCR 推論 | 42.9s／58 案 = **0.74s/案** |
| 解析＋組裝（`emit_json.build`，讀已存的框） | 1.8s／57 案 = **0.03s/案** |
| **合計** | **≈ 0.77s/案** |

⚠ **小樣本會嚴重高估。** 同一支腳本 `--limit=8` 量到 2.0s/案，是 CUDA 暖機
沒攤平；跑滿 58 案降到 0.74s。要量吞吐一律跑完整批，並把模型載入分開計。

對照 Gemini（`pred_struct`）p50 13.5s、1491 tokens/案：**PP-OCR 快約 18 倍且免費**，
58 案一輪 43s vs 約 13 分鐘。先前寫的「與 Gemini 延遲同級」不成立。
這條差距讓「PP-OCR 做即時預覽與交叉驗證、Gemini 做完整結構化」的分工更站得住
——0.77 秒可以在拍照當下跑完，13.5 秒不行。

## 2026-08-20 營養差距拆到欄位（`vs_fields.py`）——**PP-OCR 的失效是對齊，不是讀字**

`vs_gemini.py` 給的「營養 79.8% vs 96.0%」問不出下一步做什麼，拆成
欄位 × 欄 × 失效種類（漏／錯／硬填），57 案：

| | 對 | 漏 | 錯 | 硬填 |
|---|---|---|---|---|
| PP-OCR | 701 | **8** | **169** | 27 |
| Gemini struct | 843 | 3 | 32 | 1 |

**PP-OCR 幾乎不漏，全在給錯**（錯 169 : 漏 8）。最差的是糖（每欄各 18 錯）
與蛋白質（13／15），最好的是反式脂肪與飽和脂肪——順序正好是它們在標示表格裡
由下往上的位置。

那 169 個錯值追它的來源：

| 錯的值是什麼 | 格數 | 佔比 |
|---|---|---|
| **相鄰欄位的值（錯位）** | 83 | 49.1% |
| 表外／其他 | 47 | 27.8% |
| 表內他處的數字 | 22 | 13.0% |
| 另一欄的同欄位值（每份↔每100g） | 17 | 10.1% |

**約 59% 是對齊問題**（錯位 49.1 ＋ 每份/每100g 混淆 10.1），錯位方向以 +1 欄
最多（29 格，拿到下一個欄位的值）。這與 [[ocr-layer-exhausted]] 一致：
det/rec 讀得到字，是序列對齊把值配到錯的欄位。要修營養層就是修對齊，
再調 OCR 沒有用。

硬填 27 格裡有 26 格在「每100g」欄——是 `_fill` 用每一份量換算補格造成的，
GT 留 null 的地方我們算出了值。
