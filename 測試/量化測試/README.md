# 影像辨識層量化測試集

回答一個問題：**辨識層從照片上讀到的東西，跟照片上實際有的東西差多少。**

正解（`ground_truth/`）只涵蓋「照片上看得到什麼」——那是人工唯一不可取代的職責。
成分是否為添加物不在此評估，那是查表問題，另於 `eval_official_name_coverage.py`
與 `audit_additive_matches.py` 以官方清單為正解評估。

---

## 目錄

```
測試/量化測試/
├── cases.json                     案例定義（set_version / category / difficulty）
├── manifest.json                  原圖的 SHA256 清單
├── make_backup.py                 異地備份打包器（見「備份與取得位置」）
├── images/                        原圖，依類別分資料夾
│   ├── beverage/       c01_柳橙綠茶/  c02_濃豆漿/  …      25 案
│   ├── prepared_meal/  c08_椰香綠咖哩嫩雞飯/  …           17 案
│   ├── snack/                                            11 案
│   ├── instant_noodle/                                    4 案
│   └── non_food/                                          1 案
├── ground_truth/                  人工正解，同樣依類別分
│   ├── beverage/       c01_柳橙綠茶.json  …
│   ├── …
│   └── _bak_2026-07/              舊版正解備份（底線開頭＝歸檔區，不參與評分）
├── predictions/                   辨識結果，扁平放（機器產物，不需人工瀏覽）
└── results/                       每次執行的產物
    └── _baseline_2026-07-30/      0730 與 0806 報告的歷史數字
```

| 路徑 | 進版控 | 內容 |
|---|---|---|
| `cases.json` | ✅ | 案例定義 |
| `ground_truth/` | ✅ | 58 份人工正解。**唯一不可由程式重生的資產** |
| `predictions/` | ✅ | 已存的辨識結果。離線回測吃這批，不必重打 API |
| `manifest.json` | ✅ | 原圖的 SHA256 清單 |
| `images/` | ❌ | 原圖 67 張、143 MB。由 manifest 保證身分 |
| `results/` | ❌ | 每次執行的產物 |

**為何依類別分資料夾**：人工審核時看的是資料夾，不是打開 JSON 一筆筆找。
分好之後「哪一類幾件、非食品有沒有補夠」用檔案總管即可看出，
補案例時也直接看得到自己在補哪一類。

**代價與防護**：類別因此同時存在於兩處——`cases.json` 的欄位與資料夾位置。
兩者若不同步，會出現「JSON 說是零食、檔案卻在飲料資料夾」的狀態，
人工審核與程式評分看到的分類不同。`casetool.py check` 對此有專門檢查，
改分類時務必兩邊一起改（或用工具搬）。

原圖不進版控，但**測試集的可重現性不因此打折**：`manifest.json` 記下每張圖的
SHA256，圖片本體另行傳遞（見下節「備份與取得位置」），取得後放回
`images/` 跑一次 `verify` 即可確認與歷次執行用的是同一批照片。

## 取得測試集（新機器從零開始）

```bash
cd 測試/量化測試
python fetch_dataset.py            # 看本地缺什麼、有哪些備份可用
python fetch_dataset.py install    # 取得、驗雜湊、還原、自我測試
```

`install` 走完四步才算數：**找到來源 → 比對 SHA256 → 解開 → 自我測試**。
第二步不符就直接中止，一個檔案都不解——寧可沒裝，也不要裝一份不知道是什麼的。

第四步是這支存在的理由。`manifest.json` 證明的是照片的**同一性**，
不是**可用性**：雜湊全對、但 `cases.json` 少了三案的正解，照樣跑不動
而且**不會報錯**（本專案 2026-09-07 踩過同型的坑——`EMIT_READERS` 讓
119 案被靜默丟掉，指標照樣算得出來，只是分母悄悄變小）。
所以 `selftest` 逐項檢查：每案有沒有正解、正解解不解析得開、
每張被引用的照片在不在、照片內容與 manifest 符不符。

```bash
python fetch_dataset.py selftest   # 隨時可重驗；離開碼 0／1，可供 CI 使用
python fetch_dataset.py verify     # 只驗照片雜湊，不碰任何檔案
```

沒掛載 Google Drive 的機器：

```bash
python fetch_dataset.py install --from=<網址或已下載的 zip 路徑>
set FOODSCAN_BACKUP_DIR=<備份資料夾>   # 或用環境變數指定搜尋位置
```

⚠ **`install` 預設拒絕覆蓋既有的 `ground_truth/` 與 `cases.json`。**
兩份分岔的正解會讓所有跨期比較失效，而那是這個測試集唯一的價值。
要重灌得明確加 `--force`，並再打字確認一次。

## 備份與取得位置

`manifest.json` 證明的是照片的**同一性**，不是**存在性**——雜湊值對不上任何檔案時，
它只是一串無法還原的紀錄。原圖只存在 D: 一台機器上，硬碟壞掉會失去的不是照片，
是 v2.0 以來所有數字的可重現性。故另存備份，並把取得位置記在這裡：
只能驗證不能取得的清單沒有意義。

## 怎麼跑

```bash
cd 測試/量化測試

# 0. 先確認測試集完整（不符就別比數字）
python manifest_tool.py verify

# 1. 跑辨識（會打 Gemini API，要錢）
../../server/venv/bin/python run_eval.py                      # 全部
../../server/venv/bin/python run_eval.py --only-version=core48 # 只跑凍結子集
../../server/venv/bin/python run_eval.py --repeat=3            # 每案 3 次，量穩定度
../../server/venv/bin/python run_eval.py --tag=compressed_1280 # 為本次執行命名

# 2. 評分（離線，不花錢）
../../server/venv/bin/python score_eval.py
```

`EVAL_IMAGE_ROOT` 環境變數可改讀別處的圖片——影像壓縮實驗就是用這個切換壓縮前後，
不必另寫一套 harness。**該目錄底下必須也有 `images/` 這一層**：路徑是
`EVAL_IMAGE_ROOT` 加上 `cases.json` 記的相對路徑，而後者本來就含 `images/`。
少一層的話 48 案會全部「找不到圖片」被略過，而 `run_eval.py` 仍以 0 退出——
看起來像跑完了，實際一案未跑。`compress_images.py` 產生的目錄已是正確結構。

**產物**：`results/summary.json`（含切片）、`results/samples.jsonl`（逐次原始樣本）、
`results/per_case.csv`、`results/mismatches.csv`、`results/latency_vision.json`。

## 測試集版本

版號格式 **`v<主>.<次>`**，記於 `cases.json` 每一案的 `set_version`。

| 位 | 什麼時候 +1 | 對數字的意義 |
|---|---|---|
| **主版本** | 新增或移除案例 | **不可與其他主版本相比**——母體不同，比的不是同一件事 |
| **次版本** | 同一批案例，但輸入照片或人工正解有修訂 | 案例可一一對應，惟數字仍受影響，引用時須註明修訂內容 |

**已發行的版本不再更動。** 任何改動一律進新版本，舊版數字保留不刪。

理由：測試集一改，前後期數字就不是同一把尺量的。20 → 48 案時已發生過一次，
以致 2026-07-30 報告的延遲（15.9s / 29.1s）與上期（4.8s / 8.4s）不可直接相比——
案例數與擷取欄位同時變動，退步幅度無法歸因。版本化就是為了不再發生第二次。

跨期比較引用 `summary.json` 的 `slices.by_set_version.<版號>`。

## 適用範圍（2026-08-11 決定）

**本測試集只涵蓋「具有成分或營養標示的食品包裝照片」。**
不符者（食品但無標示、非食品但具標示版面、與食品無關）系統一律拒絕分析，
但**不再為其擴充案例，也不提出阻擋能力的量化指標**。

理由：「非食品」混合了三種難度相差極大的情況，混為單一類別後所得的精確率
取決於三者的比例——而比例由我們自己決定，該數字無從解讀。日後若要把這個
判斷列為貢獻，須依三種情況分別建案，而非以單一「非食品」類別擴充。

程式的相關性閘門（`server/main.py` 的 `_is_valid_food_scan()` 與 prompt 內的
相關性判斷）**維持運作**——拿掉它，模型會對無關照片生成整份營養數據。
這是適用範圍的宣告，不是功能移除。

### 非食品 15 張（已取消，保留規格供日後參考）

簡單負例（風景、收據）測不出東西，真正的風險在**看起來像食品標示的非食品**。
比例刻意偏向硬負例：

| 難度 | 張數 | 類型 | 為何選它 |
|---|---|---|---|
| 硬 | 8 | 保健食品／藥品外盒、化妝品全成分表、寵物食品、清潔劑標示 | 有營養標示或成分清單的版面結構，閘門最可能誤放。誤放後整條管線會把它當食品分析下去 |
| 中 | 4 | 藥袋、菜單、收據、營養補充品廣告 | 有文字有數字，但無標示結構 |
| 簡單 | 3 | 風景、人物、3C 產品 | 基準線 |

硬負例與測試集中既有的膠囊飲、礦物質果凍（`c22`、`c23`——是食品，但以保健
食品形態呈現）恰好是一線之隔的兩側，兩者併看才知道閘門的邊界畫在哪。
（這兩案 2026-08-11 起歸於 `snack`，不再獨立成類，但作為邊界對照的作用不變。）

### 困難食品：改為標註現有照片（2026-08-11）

> 原規劃另拍 10 張條件不佳的照片，已改為**直接標註現有案例的照片**——同一批
> 照片既已用於辨識評估，標出其拍攝條件即可切片，不需新增案例。額外的好處是
> 標到的是使用者實際拍攝時自然發生的情境，而非刻意演示的困難條件。
> 代價是各條件的案數不可控（目前曲面僅 1 案）；若某條件標完仍過少，
> 再針對該條件補拍，而非普遍新增案例。

逐張標 `difficulty`（工具見上方 `label_difficulty.py`）。詞彙表刻意只留四個
（2026-08-10 自七個縮減），並依「**重拍能不能改善**」分為兩族（2026-08-11）：

| 族 | 標籤 | 重拍有沒有用 | 失敗時的正確處置 |
|---|---|---|---|
| `shot` 拍攝造成 | `blurry` 模糊／`glare` 反光 | 有 | App 提示使用者重拍或改變角度 |
| `pkg` 包裝自帶 | `curved` 曲面／`crease` 摺痕 | **沒有** | 圓瓶仍是圓的、皺褶仍在，須由系統自行處理 |

分族有兩個作用。一是**它對應到產品該做什麼**——失敗時該不該叫使用者重拍，
取決於問題屬哪一族。二是把四個薄切片併成兩個厚的（實測 `shot` 12 案、
`pkg` 8 案，各標籤則是 1–8 案），`slices.by_difficulty_family` 即此。

**`glare` 是個例外，解讀時要小心**：概念上它屬拍攝端（換角度、避開燈源即可
改善），但實測 8 案中 7 案是零食——鋁箔材質使然。所以在目前的資料裡，
它與品項軸的共線程度接近 `pkg` 族，不可當成獨立於商品的因子看待。

**縮減理由：特徵要少到每個都養得起樣本。** 七種條件攤在少量案例上是每種 n=1，
切片無判讀價值；四種條件每種 n≥2 才有方向訊號。被移除者的去處——

- `small_text`：那是商品內容的性質，品項軸已涵蓋（`prepared_meal` 0.41 /
  `instant_noodle` 0.23 正是它），留在 difficulty 是跨軸重複計數
- `low_light`：對辨識的影響最終呈現為模糊／雜訊，由 `blurry` 承接；
  拍攝端另有閃光燈可補救
- `angled`／`occluded`：實際情境較少（使用者會對準標示拍），且遮擋的
  正解定義棘手。日後切片顯示需要時再加回並補案例

### 拍攝規範

1. **以原始解析度拍攝並保留原圖。** 壓縮由 harness 用 `EVAL_IMAGE_ROOT` 做，
   這樣同一批照片能同時服務辨識評估與壓縮實驗，不必拍兩次。
2. 一案一資料夾：`images/<case_id>/`，檔名描述內容（如 `nutrition_zh.jpg`）。
3. 拍攝當下就記下 `difficulty` 標籤——事後回想不準，而這個標籤是
   「difficult images 表現如何」唯一的依據。
4. 非食品案例的正解只需 `{"is_food_label": false}`。

```bash

#    ↑ 2026-08-14 註：那 25 件已於 08-11 整份停用，此前提不會成立，
#      故未執行合併。既有 48 案現為 v2.2（正解修訂）。理由見「版本沿革」下方說明。

# 3. 食品案例：填 ground_truth/<category>/<case_id>.json
#    照著照片上看得到的填，看不到的留 null——不可填 0，
```

## 影像壓縮實驗（2026-08-06）

回答 07-30 回饋第 5 點。App 上傳前壓縮成 **1280px 寬 / JPEG q80**
（`APP/src/components/PackageImageScanner.tsx`），問的是這樣會不會讓標示上的
小字讀不出來。

```bash
python compress_images.py                  # 產生 images_1280q80/
python compression_ab.py run --passes=3    # 兩條件各 3 遍，交錯執行，約 55 分鐘
python compression_ab.py report            # 只重新彙整既有快照，不打 API
```

**為何是 3 遍而非 `run_eval.py --repeat=3`**：`--repeat` 只把最後一次寫進
`predictions/`，而 `score_eval.py` 讀的就是那裡——重複的必須是「跑＋評分」
整組，不是只有跑。同一批圖重跑，成分 F1 實測可差 0.03 以上，跑一次分不出
訊號與雜訊。兩條件交錯跑則是為了不把時間漂移記到壓縮頭上。

### 結論（v2.1，48 案，各 3 遍）

| | 原圖 | 1280/q80 |
|---|---|---|
| 每案送出位元組 avg | 1868 KB | 294 KB |
| Gemini 視覺延遲 p50 | 11881–11994 ms | 6581–6965 ms |
| Gemini 視覺延遲 p95 | 18379–20857 ms | 9904–11787 ms |
| prompt token avg | 2712–2728 | 2673–2718 |
| `is_food_label` | 48 / 48 | 48 / 48 |
| `ingredients_flat` F1 | 0.828–0.841 | 0.862–0.881 |
| `name` 答對 | 28–31 / 46 | 32–35 / 46 |

**沒有證據顯示壓縮讓辨識變差**（`name` 與成分 F1 三遍區間不重疊、方向反而是
壓縮較好，但機制未驗證，n=3 也談不上統計顯著，不宜宣稱「壓縮讓辨識變好」）。
營養欄位的差異全在 ±1 案，且多數欄位的分母本身會隨執行浮動，不能當分數讀。

**延遲的省下來的不是推理**：token 幾乎沒變，減少的是傳輸與解碼；而這段量的是
本機到 Google，實機的 App→Fog→Cloud 傳輸段仍需另外量。

**限制**：離線壓縮用 Pillow，App 用 RN 原生編碼器，量化表、色度抽樣與縮圖演算法
皆不同（Pillow 的 LANCZOS 偏銳利，若有偏差方向大概是略偏樂觀）。故結論限於
「這個解析度與品質等級足以辨識」，不等於「App 的輸出等同於此」。後者請看
`PackageImageScanner.tsx` 的 `[compress]` log，實機拍一張即可核對。
