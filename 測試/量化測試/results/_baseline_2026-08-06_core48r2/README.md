# 基準快照 2026-08-06 — core48r2

**首次以 core48r2 實測**（重跑辨識，非離線評分）。往後的改動與這組比較。

## 測試集變更

案例仍是同樣 48 件，但每案的輸入照片經過清理：

- 移除**無實質內容的正面照**（只有商品外觀，無成分或營養標示）
- 移除 **HEIC 重複檔**與 macOS 的 `._` 中繼資料殘留
- 圖片自 **98 張降為 54 張**（167 MB → 87.5 MB），每案 1–2 張

`manifest_at_run.json` 為本次執行當下的圖片指紋，可據以確認往後的比較用的是同一批。

**core48 與 core48r2 的數字不可直接相比**——輸入變了。尤其延遲：送出的資料量
大幅下降，變快主要來自輸入變少，不是模型或程式變快。報告中須寫明原因，
不可只呈現「p50 自 15.9s 降至 11.3s」。

## 執行條件

python run_eval.py --tag=2026-08-06_cleaned_images    # 48 案，每案 1 次

## 仍未解決：幻覺與讀錯區塊

清理照片改善了分數，但**未消除**先前查明的兩種失效（已比對原始照片，正解無誤）：

- **c30_吉士豬肉堡加蛋**：0.00 → 0.26，然 `fp=69`。模型仍輸出大量標示上不存在的
  項目。原始照片的成分欄清楚可讀，模型卻自行編造合理但不實的成分清單。
- **c42_蔥鹽炙燒豬肉便當**：0.00 → 0.29，`fp=39`。原將過敏原警語誤讀為成分欄。

兩者皆非「漏抓」而是「編造」或「讀錯區塊」，**成分原文階層解析（回饋第 2 點）
無法解決**——原文本身就不對，拆得再細仍是錯的。故不應預期 prepared_meal
會因階層解析再大幅提升；該類目前 0.647，剩餘落差主要來自這兩種失效。

## c35 —— 已查明並修正

清理照片時誤留了沒有成分欄的那張，模型因而完全未輸出成分（`tp=0 fp=0 fn=56`）。
更換為含成分欄的 `IMG_4740.jpg` 並補跑後恢復：

| | F1 | 明細 |
|---|---|---|
| core48（原始輸入） | 0.30 | tp=18 fp=46 fn=38 |
| core48r2（誤留的照片） | **0.00** | tp=0 fp=0 fn=56 |
| core48r2（修正後） | 0.35 | tp=20 fp=38 fn=36 |

**此案的價值在於它證明了指標確實有在反映輸入品質**：照片換錯，分數立刻歸零；
換回來，立刻恢復。若當時只看整體 F1（0.797，仍是大幅改善），這個錯誤會被平均掉。

修正後仍僅 0.35 且 `fp=38`——該標示為三層巢狀密集小字（麵條、醬油包、麻醬包
各自展開），是 `small_text` 的典型案例，補困難度標籤時應標上。
